### พลาดตรงไหน (ไล่ด้วยโค้ดจริง)
ตัวตรวจ JS **อ่านคนละแหล่ง และคนละเวลา** กับทั้งช่องที่แสดงและตัวลงบัญชี:
1. **ไม่เคยตรวจซ้ำ** — ผูก `input` event ไว้แค่ 3 ช่อง (เลขที่/วันที่/สาขา); ช่องเลขผู้เสียภาษีเป็น readonly และถูกเขียนด้วยโค้ด
   (ไม่มี event) · `onContactChange` เติมเลขใหม่แต่**ไม่เรียกตัวตรวจ** · ตัวเติม async เขียนค่าทีหลังโดยไม่เรียกตัวตรวจ ·
   `onTaxInvoiceSourceDocSelect` / เปิดแก้ใบเก่า ก็ไม่เรียก ⇒ กล่องแดงค้างผลตอนช่องยังว่าง
2. **เปิดฟอร์มใหม่แล้วค้างของใบก่อน** — `openCreate` ล้างช่องเลขผู้เสียภาษีเป็น `''` แต่**ไม่ล้างติ๊ก "มีใบกำกับภาษีซื้อ" และไม่ซ่อน
   กล่องแดง** ⇒ ใบ PV ใบที่สองเปิดมาพร้อมติ๊กเดิม ช่องว่าง กล่องแดงของใบก่อน → เลือกผู้ติดต่อ → เลขขึ้น แต่กล่องแดงยังอยู่ = ภาพที่เจ้าของเห็น
3. **ทิศกลับ (อันตรายกว่า)** — ตัวตรวจ JS นับข้อความ `"(ผู้ติดต่อยังไม่มีเลขผู้เสียภาษี — แก้ใน Contact)"` ว่า "มีค่า" · ไม่ตรวจ checksum ·
   ไม่ตรวจที่อยู่ผู้ขาย ⇒ จอเงียบทั้งที่ตัวลงบัญชี**จะพัก 11640** และด่านอนุมัติก็ไม่มีคำเตือนเรื่องนี้ (มีแค่ "Expense ที่ไม่ติ๊กใบกำกับ")

### ผลต่อเงินภาษีซื้อ (ตรวจฝั่งเซิร์ฟเวอร์แล้ว)
- **เคสของเจ้าของ (กล่องแดงขึ้นทั้งที่มีเลข): เงินไม่ได้ถูกพักผิด** — ตัวลงบัญชีอ่าน `Contact.TaxId` จากฐาน (`0765560001108` checksum
  ผ่าน) ⇒ ถ้าผู้ติดต่อรายนั้นมีชื่อ+ที่อยู่ และใบมีเลขที่/วันที่ใบกำกับ → **ลง 11610 เคลมได้ตามปกติ** กล่องแดงเป็นคำเตือนเท็จ
  (ถ้าผู้ติดต่อรายนั้นไม่มีที่อยู่ → พัก 11640 จริง แต่ด้วยเหตุ "ที่อยู่" ไม่ใช่ "เลขผู้เสียภาษี" — กล่องเดิมบอกเหตุผิด)
- **ทิศกลับคือเงินที่ถูกพักเงียบจริง**: ผู้ติดต่อไม่มีที่อยู่ · เลข 13 หลักที่ checksum ผิด (ผ่านด่านอนุมัติ `:4784` ซึ่งดูแค่ 13 หลัก) ·
  ใบจาก API ที่ไม่มีเลขที่/วันที่ใบกำกับ → พัก 11640 โดยไม่มีคำเตือนใด ๆ → ถ้าไม่มีใครเปิดหน้า "ภาษีซื้อยังไม่ถึงกำหนด" จะพ้น 6 เดือน §82/3
  แล้วถูกล้างเป็นค่าใช้จ่าย = เสียสิทธิ์เคลมจริง

### วิธีคิดที่เพิ่ม (ไม่รื้อ)
1. **เซิร์ฟเวอร์ตัดสิน หน้าแสดงผล** — `GET /api/companies/{cid}/document/supplier-tax-invoice-check?contactId&branchCode&invoiceNumber&invoiceDate`
   (`DocumentController` · `DocumentService.CheckSupplierTaxInvoiceAsync` :4492) ใช้ **`TaxInvoiceCompletenessChecker.Evaluate` ตัวเดียวกับตัวลงบัญชี**
   + ผู้ติดต่อจากฐาน · สาขาเติมตามลำดับเดียวกับ `CreateDocumentAsync` · คืน `IsClaimable` (= ลง 11610 หรือ 11640) · `MissingFields` ·
   `MissingContactFields` (แก้ที่ผู้ติดต่อ) · `ContactTaxId` (เลขที่จะใช้เคลมจริง) · `BranchCodeError`
2. `TaxInvoiceCompletenessChecker.Result` เพิ่ม `MissingContactFields` (init property — ไม่เปลี่ยนลายเซ็นเดิม) ให้บอก "แก้ที่ไหน" โดยไม่มีสำเนากติกาใน JS
3. JS `_validateTaxInvoiceClaim` (:6033) → debounce 250ms → `_runTaxInvoiceCheck` (:6045) ถามเซิร์ฟเวอร์ · **คำตอบล่าสุดชนะ** (seq) ·
   ช่องเลขผู้เสียภาษีถูกเขียนจากคำตอบเดียวกัน (แหล่งเดียว) · ตรวจตอบไม่ได้ = บอกว่า "ยังตรวจไม่ได้" (ไม่เงียบ) · ข้อความ "จะพัก 11640"
   แสดงเฉพาะเมื่อเซิร์ฟเวอร์ว่าพักจริง · เรียกซ้ำเมื่อ: เลือกผู้ติดต่อ · เลือกใบในระบบ · เปิดแก้ใบเก่า · พิมพ์/เปลี่ยน (input+change)
4. `openCreate` ล้างติ๊ก + ซ่อนกล่อง (:7935)
5. **คำเตือนก่อนอนุมัติ** — `Helpers/InputVatParkingNotice` (pure) ต่อสายใน `CollectApprovalWarningsAsync` (:17199): ติ๊กขอเคลมแล้ว
   แต่ `Evaluate` ไม่ครบ → เตือนยอด VAT ที่จะพัก + สิ่งที่ขาด + ส่วนที่ต้องแก้ที่ผู้ติดต่อ. **จำกัดเฉพาะ `HasTaxInvoiceReference = true`**
   เพราะทางอนุมัติอัตโนมัติที่ไม่ยืนยันคำเตือน (ใบเบิกพนักงาน → PV · รายการประจำ) จะล้มทั้งเส้นถ้าเตือนใบที่ไม่ได้ประกาศเคลม

## ข้อ 5 (ส่วนผู้ติดต่อ/DBD) — "เลขภาษีเดียว หลายสาขา"

### โครงสร้างวันนี้ (verify แล้ว — ไม่ต้องเปลี่ยนโครงสร้าง ไม่มี migration)
- `Contact` มี `TaxId` + `BranchCode` + `BranchName` → **1 แถว = 1 (เลขผู้เสียภาษี, สาขา)** · `DocumentService.FindDuplicateContactAsync`
  ถือคีย์ (TaxId+Branch) อยู่แล้ว (สร้างซ้ำเลข+สาขาเดิม = คืนแถวเดิม · คนละสาขา = คนละแถว) · กลุ่มผู้ติดต่อซ้ำก็จัดด้วยคีย์เดียวกัน
- เอกสารซื้อเก็บ `SupplierBranchCode` เป็น snapshot ของใบ (รายงานภาษีซื้อใช้ค่านี้) · เอกสารขายใช้ `Contact.BranchCode` ของแถวที่เลือก
  ⇒ **โครงสร้างถูกตามประกาศอธิบดีฯ 199 แล้ว** ปัญหาอยู่ที่ "ทางเข้า" ไม่เดินตามโครงสร้าง

### วิธีคิดที่เพิ่ม
1. **`Helpers/OcrVendorBranchContact.Decide`** (pure + เทสต์) แทนโค้ด inline: เลือกแถวที่สาขาตรงก่อนเสมอ (แม้แถวเดียว) → แถวที่ไม่เคยระบุสาขา
   (พฤติกรรมเดิม — ตัวเติมเติมสาขาให้) → ไม่มีแถวตรง = ผูกแถว สนญ./แถวแรก**ตามเดิม** แต่ `MayEnrichMatchedRow = false` ⇒ ห้ามเอาที่อยู่/เบอร์/สาขาจากใบ
   ไปแก้แถวคนละสาขา + trace บอกตรง ๆ ว่าผูกกับสาขาไหนและสร้างแถวสาขาเองได้ที่ไหน · สาขาผิดรูป ("8A") = "ไม่รู้" ไม่ใช่ 00000
2. **`Helpers/RdVatBranchRecords`** (pure + เทสต์) — อ่านคำตอบ RD เป็น "รายสถานประกอบการ" จากดัชนีเดียวกันทุกช่อง · เลือกด้วย `vBranchNumber`
   จริงเท่านั้น · ลิสต์ยาวไม่เท่ากัน = ไม่ตอบ · ไม่มีเลขสาขา = ไม่ยืนยันสาขา
3. **`IDbdLookupService.GetBranchAsync(tin, branch)`** — สนญ./ว่าง = เส้นเดิมทุกประการ · สาขาอื่น = ยิง RD ด้วย `BranchNumber=n` แล้วใช้ตัวอ่านข้อ 2 ·
   ไม่ยืนยัน = null (ห้ามคืนที่อยู่ สนญ. แทน) · แคช 24 ชม./1 ชม. · `DbdCompanyResult` เพิ่ม `BranchCode`/`BranchName` (optional)
4. `OcrService.EnrichFromDbdAsync` (:4979) — ทะเบียนชนะ + ใบออกโดยสาขา → ขอที่อยู่ของสาขานั้น → `DbdAddress` = ที่อยู่สาขา (ผู้ติดต่อที่สร้างอัตโนมัติ
   ครั้งแรกจากใบ B จึงได้ **สาขา 00008 + ที่อยู่ชะอำ** ไม่ใช่ปากเกร็ด) · ทะเบียนไม่ยืนยัน = trace บอกว่าที่อยู่เป็นของ สนญ.
5. `GET /api/dbd/juristic/{id}?branch=00008` · หน้าผู้ติดต่อ: **ย้ายรหัสสาขา + ชื่อสาขาขึ้นมาแถวเดียวกับเลขผู้เสียภาษี** (เจ้าของเสนอ — เหมาะ เพราะตัวตน
   ทางภาษีของคู่ค้าคือ "13 หลัก + 5 หลัก" คู่กันเสมอ และการกรอกสาขา**ก่อน**กด DBD คือสิ่งที่ทำให้ได้ที่อยู่ของสาขานั้น) · ปุ่ม DBD ส่งสาขา ·
   ผลของสาขาเติมรหัส/ชื่อสาขาจากทะเบียน · รายการผู้ติดต่อแสดงป้ายสาขาจากเซิร์ฟเวอร์

## คำถามเจ้าของ (ห้ามเดาแทน)
1. **สแกนเจอใบของสาขาที่ยังไม่มีแถวผู้ติดต่อ (เลขภาษีมีแล้วแต่เป็นสาขาอื่น) — สร้างแถวสาขาใหม่อัตโนมัติไหม?**
   (ก) สร้างเสมอเมื่ออ่านสาขาจากป้ายกำกับได้ (≥0.85) — ข้อมูลตรงสาขาเสมอ แต่คู่ค้าค้าปลีก (Makro/Lotus/ปั๊ม) ที่ซื้อหลายสาขา = ผู้ติดต่อหลายแถว ยอดเจ้าหนี้แยกแถว ·
   (ข) สร้างเฉพาะคู่ค้าที่บริษัท "แยกสาขาอยู่แล้ว" (มี ≥2 แถวสาขา) · (ค) **ไม่สร้าง (สิ่งที่ส่งมอบตอนนี้)** — ผูกแถวเดิม สาขาของใบอยู่ที่เอกสาร
   (รายงานภาษีซื้อถูกอยู่แล้ว) ผู้ใช้สร้างแถวสาขาเองที่หน้าผู้ติดต่อ (DBD ดึงที่อยู่สาขาให้). ตัวตัดสินอยู่ใน `OcrVendorBranchContact` ที่เดียว เปลี่ยนได้ในคอมมิตเดียว
2. **ตัวค้นทะเบียนเส้นเดิม (สำนักงานใหญ่) ใช้ "ค่าแรกที่ไม่ว่างทีละช่อง"** — ถ้า RD คืนหลายสถานประกอบการ ที่อยู่อาจปนข้ามแถว. เปลี่ยนให้ใช้
   `RdVatBranchRecords` เลือกแถว `vBranchNumber = 0` ทั้งแถวไหม? (ยังไม่แตะเพราะเครื่องนี้ยิงเครือข่ายทะเบียนไม่ได้ — ควรเก็บคำตอบจริง 1 ชุดมายืนยันรูปแบบก่อน ·
   ความหมายของ `BranchNumber=n` ใน SOAP ก็เป็นข้อสันนิษฐานจากรูปแบบที่ตัวอ่านเดิมรองรับอยู่ ต้องลองกับของจริง)
3. แถวผู้ติดต่อสำนักงานใหญ่ที่อาจเคยถูกที่อยู่ของใบสาขาทับ (เฉพาะแถวที่ OCR สร้าง/แก้ + ทะเบียนยืนยัน) — ต้องการรายงานให้ตรวจไหม (ตรวจย้อนแบบแน่นอนไม่ได้)
4. ทางเข้าอื่น 7 จุดที่หาผู้ติดต่อด้วยเลขภาษีอย่างเดียว (integration/import/POS/ที่พัก/API v1) — ให้ใช้คีย์ (เลขภาษี + สาขา) แบบ `FindDuplicateContactAsync` ทั้งหมดไหม
   (payload ส่วนใหญ่มีช่องสาขาอยู่แล้ว)
5. ป้ายพิมพ์บนเอกสาร: `TaxBranchCode.Label` พิมพ์ "สาขาที่ 8" (ตัดศูนย์นำ) · CLAUDE.md §A เขียน "สาขาที่ {code}" · โจทย์ยกตัวอย่าง "สาขาที่ 00008" —
