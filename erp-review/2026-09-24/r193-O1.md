### ข้อ 10 — e-Tax XML จริงของ Shopee (`ETDA-invoice.xml` ใน PDF จาก pdfmake)
ช่องว่างที่พบและแก้ใน `Services/Implementations/Ocr/EtaxPdfXmlExtractor.cs`:
1. `FindFilespecXmlRef` — `IndexOf(b, −1)` โยน exception เมื่อ Filespec ตัวแรกไม่ใช่ .xml ⇒ ทั้งไฟล์ตกไป OCR เงียบ ๆ
2. ชื่อไฟล์ hex UTF-16 (`<FEFF…>`) ที่ PDFKit ใช้ — อ่านไม่ได้
3. `FindFilespecPointingTo` — regex ไม่เคยแมตช์ ⇒ ชื่อไฟล์ "embedded.xml" เสมอ
4. `ReadStream` — หาคำ "stream" ตัวแรก ⇒ dict ที่มี `octet-stream` ตัดสตรีมผิดตำแหน่ง
5. ยอดบรรทัดอยู่ใน `NetLineTotalAmount` (ไม่มี `LineTotalAmount`) ⇒ ยอดบรรทัดว่างทุกบรรทัด
6. BOM นำหน้า ⇒ `XDocument.Parse` ปฏิเสธ
7. `T03` (ใบเสร็จ/ใบกำกับ) ถูก map เป็น Receipt ⇒ กระดาษถูกตีว่าไม่ใช่ใบกำกับ → ตาราง ETDA ครบ (`MapTypeCodeToInternal` เปิดเป็น `internal` ให้เทสต์)

ยอด XML เป็นตัวตั้งที่แข็งที่สุด (ไม่ผ่านขั้นยึดยอด) · ข้อความหน้า PDF (`PdfTextLayerExtractor`) ใช้หา**เฉพาะ**การปรับตอนชำระที่ XML ไม่มี
(`OcrService.cs:331` + `ApplyEtaxSettlement` `:7221`) ⇒ ใบ Shopee ที่เป็น XML ได้ `[PAY≠TOTAL]` + `[PAY-PLAN]` เหมือนใบ PDF

## 5. คำถามค้าง / ความเสี่ยงที่ต้องให้เจ้าของหรือทีมอื่นตัดสิน

1. **`ApprovalService` (workflow อนุมัติหลายขั้นบนเว็บ)** ส่ง `acknowledgeWarnings:true` ภายใน ⇒ คำเตือน [Σ-GAP] ไม่ขึ้นบนเส้นนั้น (ตามโจทย์ "ภายในคงเดิม") — ต้องการให้ขึ้นไหม
2. **ใบตั้งหนี้ (PI/Expense) จากสแกน** ยังติด [PAY≠TOTAL] (ไม่อนุมัติเอง) จนกว่าจะบันทึกการชำระ — เพราะบรรทัดปรับอยู่ที่การชำระ ไม่ใช่ที่เอกสาร · ถ้าต้องการ 1-click ต้องตัดสินว่า "ข้อเสนอที่รอชำระ" ปลดได้ไหม
3. **กระทบยอดธนาคาร**: PV จ่ายในตัวยังมี `TotalAmount`/`PaidAmount` = 536 ขณะที่เงินออกจริง 438 (JE ถูก — ขาเงินสดสุทธิ 438) — ตัวจับคู่ statement ที่เทียบยอดเอกสารจะเห็น 536 ≠ 438 · ควรให้ตัวจับคู่อ่าน `ActualPaidAmount` (ทีม F/E)
4. **พรีวิว JE ก่อนอนุมัติ (projected GL)** ไม่รวม adjusting lines/ขาส่วนต่าง/ขาปัดเศษ — ผู้ใช้จะเห็นพรีวิวต่างจาก JE จริงเศษ/ส่วนต่าง
5. **`TaxService` ฐาน VAT ใช้ `SubTotal`** — ถูกตามกระดาษแล้ว (4,695.33) แต่รายงานที่รวมจาก `Σ Line.Amount` จะต่าง 0.01 ต่อใบที่มีผลต่างปัดเศษ — ควรตรวจรายงานที่อ่านรายบรรทัด
6. **เส้น UI handoff/สร้างจากหน้าอื่น** (เช่น convert/clone/recurring) — `RoundingAdjustment`/`ActualPaidAmount` **ไม่สืบทอด** ไปเอกสารลูก (ตั้งใจ: ผลต่างปัดเศษเป็นของบรรทัดชุดนั้น · ยอดชำระจริงเป็นของการจ่ายครั้งนั้น) — ยืนยันว่าถูกต้องตามกฎ #4 A "เอกสารลูกสืบทอด"
7. ผัง 51150 มีเฉพาะบริษัทที่มี 11500 (migration เดิม) + บริษัทใหม่ — บริษัทเก่าที่ไม่มีจะได้ข้อความ "ไม่พบผังบัญชี 51150" ตอนบันทึก (ทางไปต่อ: เพิ่มผัง) · ต้องการ migration ใส่ให้ทุกบริษัทเหมือน 54960 ไหม
8. `MapTypeCodeToInternal` เปลี่ยนเป็น `internal` (เดิม `private`) เพื่อเทสต์ · ฝั่งขาออก `EtaxDocumentTypeMap` ส่ง `Receipt → T03` — ETDA T03 = ใบเสร็จ/ใบกำกับภาษี ถ้าเอกสาร Receipt ไม่ใช่ใบกำกับจริงควรเป็น T01 (นอกขอบเขต O1 — ฝากทีม E ตรวจ)
9. F3 ข้อ 11 (ฝ่ายค้าน): agent นี้ไม่มีเครื่องมือเรียก subagent — ตรวจเองตาม 3 คำถาม (ทางเข้าอื่น · ทิศตรงข้าม · สถานะประทับเอง) แล้วบันทึกข้างบน · **ขอให้ main agent ส่ง diff เงิน/ภาษีรอบนี้ให้ฝ่ายค้านอีกรอบ**

"ระบบใช้ลายเซ็นเดิม" · `UpdateDocumentAsync` ไม่แตะ `DocumentApproval`) · B9 ตรง (กันซ้ำด้วย `AnyAsync` อย่างเดียว) · ยังไม่ได้คอมไพล์ในเครื่องนี้

| ข้อ | สิ่งที่แก้ | จุดต่อสาย |
|---|---|---|
| R3-3 | **ตัวตั้ง canonical ตัวเดียว** `Helpers/DocumentSignedContent.Hash(doc, lines)` (`v1:` + SHA-256 · ครอบผู้ซื้อ · สกุลเงิน/อัตรา · ราคารวม VAT · ส่วนลดท้ายบิล · ยอดหัวเอกสารทุกช่อง · ครบกำหนด/เครดิต/เงื่อนไขชำระ/หมายเหตุ · ทุกบรรทัดที่ลูกค้าเห็น · ไม่ครอบผังบัญชีภายใน) — เขียนตอนเซ็นลง `DocumentApproval.SignedContentHash` และคำนวณซ้ำตอนเรียกซ้ำด้วยฟังก์ชันเดียวกัน · `CanReuseSignature` ใช้ลายเซ็นเดิมได้เฉพาะ hash ตรง **และ** คำขอเป็นลายเซ็น/ชื่อเดิม (hash ว่าง = แถวก่อนรอบนี้ = ไม่รู้ ⇒ ใช้ซ้ำไม่ได้) · อย่างอื่น ⇒ ลายเซ็นเดิมถูก "แทนที่" (soft-delete ทั้งขั้นและ `DocumentSignature` + หมายเหตุเหตุผลใน `Comments` ⇒ ไม่ขึ้น PDF · ไม่นับเป็นขั้นที่ผ่าน) แล้วบันทึกลายเซ็นใหม่จากคำขอ (ไม่ทิ้งเงียบ) · ผู้อนุมัติที่ประทับ = ผู้เซ็นที่เก็บไว้เมื่อใช้ซ้ำ · ข้อความ 422 เลิกสัญญา "ใช้ลายเซ็นเดิม" แบบไม่มีเงื่อนไข (ใช้ต่อได้เฉพาะไม่แก้เนื้อหา · แก้แล้วต้องเซ็นใหม่) · ข้อความสำเร็จบอกเมื่อใช้ลายเซ็นที่เก็บไว้ | `SignatureApprovalService.ExternalApproveQuotationAsync` · entity `DocumentApproval.SignedContentHash` · `DatabaseMigrationHelper` (ADD COLUMN) |
| B9 (PLAUSIBLE) | ล็อกแถวเอกสาร `FOR UPDATE` ใน transaction ครอบ "ตรวจ → บันทึกลายเซ็น" (pattern เดียวกับ `ApproveDocumentAsync`) + อ่านสถานะ/เนื้อหาใหม่ใต้ล็อก ⇒ คำขอที่สองรอ แล้วเห็นลายเซ็นของตัวแรก (ใช้ซ้ำ ไม่ซ้ำแถว) · ไม่ใช้ unique index เพราะฐานที่ใช้งานมีแถวซ้ำจากพฤติกรรมเดิมแล้ว (สร้าง index จะล้มตอน migrate) · ครั้งที่สองที่ชนการอนุมัติของตัวแรก: ถ้าใบอนุมัติแล้วจริง ⇒ ไม่ตอบ 422 หลอก และไม่แปลงเอกสารซ้ำ | เดียวกัน |

กติกา `required_call_site_check` ของ `ExternalApproveQuotationAsync` เปลี่ยนจาก `if (!alreadySigned)` เป็น: ต้องเรียก `DocumentSignedContent.Hash(` ·
`CanReuseSignature(` (ส่ง `request.SignatureData`) · เขียน `SignedContentHash = contentHash` · `SupersedeCustomerSignature(` · มี `FOR UPDATE` ·
การตัดสินใช้ซ้ำ/แทนที่ต้องมาก่อนเพิ่ม `DocumentSignature` — negative test ในตัวผ่าน (90 กติกา)

เทสต์ `DocumentSignedContentTests` สองทิศ: แก้ราคา/จำนวน/ผู้ซื้อ/ครบกำหนด/เครดิต/เงื่อนไข/หมายเหตุ/เพิ่ม-ลบบรรทัด/ส่วนลดท้ายบิล/ราคารวม VAT ⇒ ต้องเซ็นใหม่ ·
แถวเก่าไม่มี hash ⇒ ใช้ซ้ำไม่ได้ · ลายเซ็น/ชื่อใหม่ ⇒ บันทึกใหม่ · ขอบเขตช่องเลื่อนไม่ได้ ‖ เนื้อหาเดิม + ลายเซ็นเดิม ⇒ ใช้ซ้ำ · ลำดับบรรทัดจาก DB /
scale ทศนิยม / ช่องว่าง / CRLF / ผังบัญชีภายใน / บรรทัดที่ลบแล้ว ⇒ ไม่นับเป็นการแก้

ไม่ได้ทำ (ตั้งใจ): `UpdateDocumentAsync` ไม่ล้างขั้นลูกค้า — การตรวจอยู่ที่จุดใช้ลายเซ็น (ครอบทุกทางแก้: เว็บ/API/นำเข้า) ดีกว่าไล่ทุกทางเขียน ·
ลายเซ็นขั้นภายใน (`ApproveAsync`) ยังไม่บันทึก hash — ขั้นภายในไม่มีการ "ใช้ซ้ำ" (เซ็นแล้วผ่านทันที) ถ้าจะให้แก้เนื้อหาแล้วขั้นภายในเป็นโมฆะเป็นงานออกแบบแยก

```
**330 ไฟล์ · 2,856 `[Fact]` + 444 `[Theory]` (1,933 `InlineData`)** ณ 2026-09-24 — pure-logic ทั้งหมด (0 ไฟล์แตะ `DbContext`)
```

doc ที่ต้องขยับ (ห้ามแตะรอบนี้): DOCUMENT_FLOW — ลายเซ็นลูกค้าใช้ซ้ำได้เฉพาะเนื้อหาเดิม (hash) · เนื้อหาเปลี่ยน ⇒ ลายเซ็นเดิมถูกแทนที่ + ต้องเซ็นใหม่ · ล็อกแถวเอกสาร

## หลังฝ่ายค้านรอบสี่ (review193-r4.md)

ยืนยันด้วยการเปิดไฟล์ก่อนแก้: R4-1 ตรง (ด่านเซ็นครบ `ApproveDocumentAsync` นับทุกแถว Approved โดยไม่ดู hash · PDF ช่องลูกค้าพิมพ์แถวล่าสุดที่มี
`SignatureData` · ข้อความ 422 ชี้ไปหน้าเอกสาร) · R4-2 ตรง (hash ไม่ครอบข้อความที่พิมพ์บนใบหลายช่อง) · พบเพิ่มเอง: ลายเซ็นคู่ค้าข้ามบริษัท
(`CrossTenantWorkflowService.ApproveIncomingAsync` บทบาท Customer) ไม่บันทึก hash = ทางเข้าที่สามของลายเซ็นลูกค้า · ด่านเซ็นครบทำงานเฉพาะเมื่อเปิด
`RequireApprovalForDocuments` — ปิดอยู่ ⇒ อนุมัติที่หน้าได้เสมอ แล้ว PDF ของใบที่อนุมัติ (เนื้อหาล็อก) จะพิมพ์ลายเซ็นเดิม ⇒ ต้องแทนที่ลายเซ็นตอนอนุมัติด้วย ·
ยังไม่ได้คอมไพล์ในเครื่องนี้

| ข้อ | สิ่งที่แก้ | จุดต่อสาย |
|---|---|---|
| R4-1 | **ตัวตัดสินตัวเดียว** `DocumentSignedContent.IsSignatureCurrent(approval, doc, lines)`: ขั้นภายใน ⇒ ไม่อยู่ในกติกา · เอกสารออกแล้ว (`DocumentStatusRules.IsIssued` — เนื้อหาล็อก) ⇒ นับ (ใบเก่า/แถวไม่มี hash ยังพิมพ์ลายเซ็นเดิม — §H) · ร่าง/รออนุมัติ/ถูกปฏิเสธ ⇒ นับเฉพาะ hash ตรง (ไม่มี hash / v1 = ไม่นับ) · ข้อความเดียว `StaleReason` "ต้องให้ลูกค้าเซ็นใหม่เพราะเนื้อหาเปลี่ยน…" · ตัวแทนที่ `Supersede` ย้ายเข้า helper (ใช้ร่วมสองเส้น) | (1) `DocumentService.ApproveDocumentAsync` — คำนวณชุดลายเซ็นที่ไม่นับ**ก่อน**ขั้นซ่อมบรรทัด · ด่านเซ็นครบไม่นับ + 422 `SIGN-CUSTOMER-STALE` · ในธุรกรรมอนุมัติ ลายเซ็นที่ไม่นับถูกแทนที่ (soft-delete + เหตุผล) ⇒ PDF หลังอนุมัติพิมพ์เฉพาะลายเซ็นที่ตรงเนื้อหา · (2) `CheckAllApprovedAndProcessAsync` — เซ็นครบแต่ลายเซ็นลูกค้าไม่นับ ⇒ 422 พร้อมทางไปต่อ · (3) PDF `ResolveSignersAsync` (ใช้ร่วม HTML + QuestPDF) · (4) API `GetDocumentWithApprovalsAsync` (แถวไม่นับได้ `SignatureStaleReason`) + `GetDocumentSignaturesAsync` (ไม่ส่งภาพลายเซ็นที่ไม่นับ) · (5) `CrossTenantWorkflowService.ApproveIncomingAsync` บันทึก hash · ข้อความ 422 ของลายเซ็นลูกค้าบอกว่าแก้เนื้อหาแล้วลายเซ็นใช้ไม่ได้**ทั้งสองทาง** |
| R4-2 | `Hash` เป็น `v2`: เพิ่ม วันที่เอกสาร · วันส่งมอบ · `CustomTermsAndConditions` · `CustomAppendix` · `CustomFooterNotes` · `BankAccountId` · `DocumentLanguage` · `BrandId` · `IssuerBranchCode` · `Reference` · `BookingNumber` · `DepositAppliedRef` · `DepositAppliedAmount` · `DepositBaseDeducted` · `PaymentType` (ไล่จากทุกช่องที่ renderer ทั้งสองอ่านจาก `Document`) · ไม่ครอบ: `DocumentTemplateId` (หน้าตา) · `PreparerName` · ผังบัญชี/โปรเจกต์ · ช่องที่เกิดหลังอนุมัติ (เลข/สถานะ/ยอดชำระ) · ลายเซ็น v1 = แถวเก่า | `Helpers/DocumentSignedContent.cs` |

กติกา `required_call_site_check` (122 กติกา · negative test ในตัวผ่าน): ต้องเรียก `IsSignatureCurrent(` ใน `ApproveDocumentAsync` (ก่อน `LinesStoredGross(`) +
`Supersede(` + ด่านเซ็นครบใช้ชุดที่ไม่นับ · `ResolveSignersAsync` · `CheckAllApprovedAndProcessAsync` (ก่อนเรียกอนุมัติ) · `StaleSignatureApprovalIdsAsync` ·
`GetDocumentWithApprovalsAsync`/`GetDocumentSignaturesAsync` เรียกตัวนั้น · `ApproveIncomingAsync` เรียก `Hash(` · กติกาเดิมของ `ExternalApproveQuotationAsync` เปลี่ยนเป็น `DocumentSignedContent.Supersede(`

เทสต์ `DocumentSignedContentTests` เพิ่มสองทิศ: แก้ช่อง v2 ทีละช่อง (14 เคส) ⇒ ต้องเซ็นใหม่ · v1 ≠ v2 · ร่างแก้แล้ว/ไม่มี hash/v1 ⇒ ไม่นับ ‖ ร่างเนื้อหาเดิม ⇒ นับ ·
ใบออกแล้ว (Approved/Sent/Paid/Voided) + แถวไม่มี hash ⇒ ยังนับ (§H) · ขั้นภายในไม่ถูกตัดสินด้วย hash · ลายเซ็นคู่ค้า External อยู่ในกติกา · `Supersede` เก็บเหตุผลต่อท้ายหมายเหตุเดิม
