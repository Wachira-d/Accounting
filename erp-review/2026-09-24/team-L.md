### วิธีคิดที่เพิ่ม — `Helpers/OcrDateReader` (ขั้นตรวจท้ายสุดของทุก engine · `OcrService.cs:587` ก่อนด่านคณิตและก่อน sync ลงแถวสแกน · ข้าม e-Tax XML)

1. **ป้ายชนะตำแหน่ง** — วันที่ที่มีป้าย "วันที่/Date/ลงวันที่" ชนะวันที่ลอย ๆ · วันที่ที่มีป้าย**ชนิดอื่น** (ครบกำหนด/Due/พิมพ์/หมดอายุ/ส่งของ/ถึงวันที่) **ไม่มีสิทธิ์**เป็นวันที่เอกสาร ·
   ป้ายชนิดอื่นที่จบชิดหน้าป้ายวันที่ (≤ 2 ตัว: "Due Date" · "Expiry Date") = ป้ายเดียวกัน · ป้ายชนิดอื่นที่อยู่ห่าง ("โรงพิมพ์…วันที่") ไม่นับ ·
   ป้ายบรรทัดบน (แบบฟอร์ม) นับด้วย
2. **แบบไทยก่อน** — ตัวเลขสามก้อน = วัน/เดือน/ปี · ปีผ่าน `ThaiDate.NormalizeYear` ตัวเดียว (26 = ค.ศ. 2026 · 69 = พ.ศ. 2569) · ถ้าแบบไทยไม่สมเหตุสมผลค่อยใช้แบบอื่น ·
   ชื่อเดือนไทย/อังกฤษต้อง**ตรงทั้งคำ** (`ThaiMonthName.TryParseExact` ใหม่ — "market"/"mayor" ไม่ใช่เดือน)
3. **ปีต้องใกล้วันอัปโหลด** (`MaxPastDays = 730` · `MaxFutureDays = 31`) — ใช้**เลือกการตีความ**และ**ลดความมั่นใจ** ไม่ล้างทิ้ง
4. **เทียบกับ engine**: ตรงกัน → Confirmed · engine อ่าน**ก้อนเดียวกันแต่เรียงผิด** → ใช้แบบไทย · engine หยิบ**วันที่อีกก้อนที่มีป้ายชนิดอื่น** → ใช้ก้อนที่มีป้ายวันที่ ·
   engine ห่างวันอัปโหลดเกินช่วงและไม่อยู่บนกระดาษ → ใช้ป้าย · ขัดกับป้ายแต่ engine สมเหตุสมผล → คงค่า engine + คะแนน 0.60 · ไม่มีป้าย → ไม่แตะ engine
5. ค่าที่ทับ engine = **0.80** (< 0.85 ⇒ ไฮไลต์เหลือง · DOCTRINE G4) · ที่มา = `PaperLabel` เมื่อมาจากป้าย · `Engine` เมื่อไม่มีป้าย

ไล่กระดาษจริง: ใบ A (Wine Pro `Date: 18/09/26 6:35 PM`) python → null ⇒ **เติม 2026-09-18** · Azure ถ้าได้ 2018-09-26 ⇒ **ทับเป็น 2026-09-18** ·
ใบ B (Radisson `วันที่ DATE 12/09/26`) Azure ถ้าได้ 2026-12-09 หรือ 2012-09-26 ⇒ **ทับเป็น 2026-09-12** · ถ้า engine ถูกอยู่แล้ว ⇒ Confirmed ไม่แตะ

## 3. local จับที่อยู่ผู้ซื้อไม่ได้ — ต้นเหตุ

ไล่ด้วยข้อความจริง (จำลอง regex เดิมด้วย python):
- **ไม่มีตัวอ่านที่อยู่ผู้ซื้อเลยทั้งเรพ** — `BuyerAddress` ถูกเขียนแค่จาก Azure `CustomerAddress` (:3410) · e-Tax XML · คำแก้ผู้ใช้ · ก้อนที่สองของที่อยู่ที่ถูกต่อกัน (`SmartFieldExtractor.cs:330`) · python ไม่มีช่องนี้
- **แย่กว่านั้น: ที่อยู่ของเราไปอยู่ช่องผู้ขาย** — `VendorAddressRegex` (:39) หยิบป้าย "ที่อยู่/ADDRESS" **ตัวแรกของหน้า**: ใบ B หัวร้านไม่มีป้าย "ที่อยู่" ⇒ ได้
  `"Address  202/24 หมู่ที่5 … 20110"` (= ที่อยู่ **หจก.แอม แฮปปี้เนส**) เป็น**ที่อยู่ผู้ขาย** ทั้งใน `ParseThaiDocument` (Tesseract) และ `EnrichFromRawText`
  (ทุก engine ที่ไม่ได้ที่อยู่ผู้ขายมา รวม Azure) — แล้วถ้าเป็นเส้น Azure ค่านี้ยัง**ถูกสอนเข้าคลัง known-good** ด้วย · ใบ A ป้าย "Address" อยู่บรรทัดของตัวเองแล้วตามด้วย
  ที่อยู่ 2 บรรทัดที่ไม่มีบรรทัด "Tel/เลขประจำตัว" ปิด ⇒ regex เดิมไม่แมตช์เลย (ทั้งสองช่องว่าง)

### วิธีคิดที่เพิ่ม — `Helpers/OcrBuyerAddressReader` (ต่อสายใน `EnrichFromRawText` `OcrService.cs:8834` — ทุก engine · เติมเฉพาะช่องว่าง)
- จุดยึด = ป้ายฝั่งผู้ซื้อจาก `OcrPartyLabels.FindAll` (**ตัวค้นป้ายตัวเดียวของระบบ** — ไม่ได้เขียนตัวแยกโซนชุดที่สอง) · ถ้ารู้เลขผู้ซื้อ ใช้ป้ายที่อยู่เหนือเลขนั้น
- มองหาป้าย "ที่อยู่/Address" ใต้จุดยึด ≤ 8 บรรทัด **ไม่ข้ามป้ายฝั่งผู้ขาย** · กินป้ายสองภาษา · ต่อบรรทัดต่อเนื่อง ≤ 3 บรรทัดจนเจอรหัสไปรษณีย์หรือป้ายช่องอื่น (โทร/เลขประจำตัว/สาขา/รายการ/วันที่)
  · ต่อคำที่เครื่องพิมพ์ตัดกลางชื่อสถานที่ (`ต.บาง` + `พระ` = `ต.บางพระ`) · ค่าต้อง "หน้าตาเป็นที่อยู่" (รหัสไปรษณีย์ หรือคำบอกที่อยู่ ≥ 2) · ไม่มีป้ายผู้ซื้อ = ไม่เดา · คะแนน 0.80
- **invariant ใหม่**: ที่อยู่ผู้ขายที่เป็น**ส่วนหนึ่งทั้งก้อน**ของบล็อกผู้ซื้อ ⇒ ล้างจากช่องผู้ขาย (คะแนน 0.30 ⇒ ไฮไลต์ · DBD/ประวัติเติมที่อยู่จริงในชั้นถัดไป) ·
  ที่อยู่ผู้ขายที่ยาวกว่า (มีที่อยู่ร้านนำหน้า) **ไม่ถูกล้าง** — กันลบข้อมูลร้าน · รันก่อนตัวสอนคลัง ⇒ Azure ไม่สอนที่อยู่เราเป็นที่อยู่ผู้ขายอีก
