## 2. ข้อที่ verify แล้ว "ไม่จริง/ไม่ตรง"
1. **คำสั่ง S-04 "แคชสั้นแบบเดียวกับที่ middleware แคชสถานะคีย์"** — middleware **ไม่ได้แคชสถานะคีย์** (แคชเฉพาะผล BCrypt · สถานะ Revoked/Expired/IsActive อ่าน DB ทุก request ตามคอมเมนต์ `VerifyKeyCached`) ⇒ ทำแบบเดียวกับสถานะคีย์จริง = อ่าน DB ทุก request (query เดียว ดัชนี CompanyId) · เหตุผลเพิ่ม: กรณีใช้งานคือ "สงสัยคีย์รั่ว" ต้องมีผลทันที และแคช static ต่อเครื่องขัดกฎ #4 D (หลายเครื่องปิดไม่พร้อมกัน)

### 9.2 W2-C1 (ข) — ทำไมยังไม่ serialize (เปรียบเทียบสองทาง)

| | `pg_advisory_xact_lock` ต่อบริษัทตอนประทับ | sealer job ตัวเดียว (`JobLock` + watermark) |
| --- | --- | --- |
| กันแตกกิ่งได้ไหม | ได้ **ก็ต่อเมื่อ** ถือล็อกตั้งแต่อ่านปลาย chain จน commit ของ transaction ชั้นนอก — แต่ `SaveChangesAsync` ประทับหลัง `base.SaveChangesAsync` รอบแรก และ service ใช้ `BeginTransaction` ~98 จุด ⇒ ล็อกต้องอยู่ถึง commit ของ service | ได้ — ประทับหลัง commit ตามลำดับของ job เอง |
| ความเสี่ยง | **deadlock** (A ถือ row lock รอล็อก audit · B ถือล็อก audit รอ row lock เดียวกัน) + การเขียนทุกครั้งของบริษัทเรียงคิวทั้ง transaction (POS/งานกลางคืน/integration ชนกันตลอด) | ช่วงเวลาที่แถวยังไม่มี hash (หน้าต่างแก้ได้โดยไม่ถูกจับ) · ต้องเพิ่มคอลัมน์ `ChainSeq` (ADD COLUMN IF NOT EXISTS) + ตัวตรวจเรียงตาม `ChainSeq` · เปลี่ยนความหมาย "แถวที่ RowHash=null" (ตอนนี้ = นอก chain) |
| ขนาดงาน | เล็กในโค้ด แต่กระทบทุกคำขอเขียน — ต้องวัดก่อน | สถาปัตยกรรมใหม่ (job · คอลัมน์ · migration ความหมาย · ตัวตรวจ) |

ข้อเสนอ: **sealer job** ปลอดภัยกว่า (ไม่มี deadlock · ไม่เพิ่ม latency ของคำขอ) แต่เป็นการเปลี่ยนสถาปัตยกรรม ⇒ ตามคำสั่งจึงทำ (ก) ก่อน: ตอนนี้ fork **ไม่ถูกรายงานว่าเป็นการแก้** และไม่บังการแก้จริง ⇒ ผลเสียที่ยังเหลือของการแตกกิ่งคือ "chain มีกิ่ง" (ยังตรวจเนื้อทุกแถวได้ครบ) ไม่ใช่การแจ้งเตือนหลอก
