## 2. เลือกทางไหน · ทำไม

- **"ไม่ได้จ่ายอะไรเลย = ฐาน 0"** ใช้เงื่อนไข `statutoryWage ≤ 0 && grossIncome ≤ 0` ไม่ใช่ค่าจ้างอย่างเดียว — ฐานค่าจ้างของระบบนับแค่
  เงินเดือน + เบี้ยเลี้ยงที่ติ๊ก ⇒ พนักงานเงินเดือนฐาน 0 ที่ได้คอมมิชชันจริงยังคิดขั้นต่ำ 1,650 **เหมือนเดิมทุกสตางค์** (ถ้าตัดเป็น 0 = นำส่งขาดเงียบ · DOCTRINE G5)
- **คำนวณใหม่ = HR กดเอง ไม่อัตโนมัติ** — รอบที่ Calculated/Approved เป็นตัวเลขที่คนดู/อนุมัติแล้ว การเปลี่ยนเงียบ ๆ ตอน deploy
  = "สถานะที่ระบบประทับเอง" · ปุ่ม "🔄 คำนวณใหม่" มี confirm บอกผลข้างเคียง (ยอดแก้มือรายคน + แหล่งจ่ายรายคนถูกแทน · อนุมัติแล้วต้องอนุมัติใหม่)
- **เคยจ่ายแล้วกลับรายการ (`ReopenedAt`) ห้ามคำนวณทั้งรอบ** — ยอดชุดเดิมอาจอยู่ใน ภ.ง.ด.1/สปส.1-10 ที่ยื่นแล้ว ("จ่าย/ยื่นแล้วห้ามแก้")
  ทางไปต่อ = "✏️ แก้ยอด" รายคนที่มีร่องรอย
- **TaxId ชนะ CitizenId** — ช่องที่ HR กรอกเองชัดที่สุด (ต่างด้าวมีแต่เลขผู้เสียภาษี) · ข้อมูลเดิมไม่ขยับเพราะ `TaxId` ไม่เคยมีผู้เขียน
  (ไฟล์ยื่นที่เคยใช้ `CitizenId ?? TaxId` ให้ผลเท่าเดิมทุกแถว)
- **เลขผู้เสียภาษีของพนักงานปิดบังแบบเลขบัตร** (`1-XXXX-XXXXX-XX-8`) ไม่ใช่ `PiiMask.TaxId` (เปิด 7 หลัก — ใช้กับนิติบุคคล) · คอลัมน์เข้ารหัสอยู่แล้ว (`EncryptedColumnConverter` · `AccountingDbContext.cs:1489`) ไม่ต้องมี migration
- **checksum เลขบัตรตอนสร้าง/แก้** ผ่าน `ThaiTaxIdValidator` กลาง (เดิม regex 13 หลักล้วน) — แต่ "เลขเดิมที่ไม่ได้แก้" ถูกตรวจ**ก่อน** checksum
  ⇒ เลขเก่าที่เข้าระบบก่อนมีด่าน ไม่ทำให้ HR แก้ช่องอื่นไม่ได้ (เทสต์ `เลขเก่าที่checksumไม่ผ่านแต่ไม่ได้แก้_ไม่บล็อกการแก้ช่องอื่น`)
- **วันเริ่มงานส่งเฉพาะเมื่อเปลี่ยนจริง** (`dataset.orig`) — กันการแปลงเขตเวลาไป-กลับขยับค่าเดิม (ซึ่งกระทบ `PayrollProration`)

## 4. F3 ข้อ 7–12

7. **รูปแบบเดิมเหลือกี่จุด** — `emp.TaxId` เดี่ยว ๆ: 0 · fallback มือ `CitizenId ?? TaxId`/`TaxId ?? CitizenId`: 0 (6 จุดย้ายเข้า resolver + 2 จุดใน `TaxService` ที่ใช้ `CitizenId` ตรง) ·

   ที่ยังใช้ `emp.CitizenId` ตรงอย่าง**ถูกต้อง**: ไฟล์ สปส.1-10 ×3 (`TaxFilingExportService.cs:465,636,679`) — สปส. ใช้เลขบัตร ไม่ใช่เลขผู้เสียภาษี
8. **ทางเข้าอื่น** — คำนวณเงินเดือนมีทางเดียว (`POST runs/{id}/calculate`) · รอบนำเข้า (TakeTime) ไม่ผ่านสูตรเรา และถูก `CanRecalculate` กันไม่ให้ทับ ·
   แก้พนักงาน: เว็บ 2 หน้า → endpoint เดียว (`UpdateEmployeeAsync`) · **ยังไม่เดินด่าน checksum**: HRIS sync (`SyncEmployeesAsync`) และนำเข้า CSV
   (`ImportExportService.cs:1428`) — ตั้งใจไม่เข้มขึ้นรอบนี้ เพราะแถวที่ถูกปฏิเสธ = พนักงานหายจากรอบเงินเดือน (แย่กว่าเลขผิด) ⇒ เสนอเป็นคำเตือนต่อแถว (backlog)
9. **เข้มขึ้น** — (ก) checksum เลขบัตรตอนสร้าง: ผู้ใช้เห็นข้อความ "เลขบัตรประชาชน: เลข check digit ไม่ถูกต้อง…" แก้เลขแล้วบันทึกใหม่ได้ ·
   เทสต์ทิศตรงข้าม `เลขเก่าที่checksumไม่ผ่านแต่ไม่ได้แก้_ไม่บล็อกการแก้ช่องอื่น` · `ไม่ส่งช่อง_ไม่แตะ` (ข) แก้รหัสพนักงานที่มีประวัติเงินเดือน:
   ช่องล็อกพร้อมเหตุผลตั้งแต่เปิดฟอร์ม · เทสต์ `รหัสเท่าเดิม_ไม่ถูกด่านประวัติเงินเดือนกัน` (ค) คำนวณใหม่: **ผ่อนลง** (เดิม Draft อย่างเดียว) — รอบที่ถูกปฏิเสธเห็นปุ่ม 🔒 + เหตุผล
