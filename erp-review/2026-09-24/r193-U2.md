### ก่อนแก้ (ไล่จากโค้ดที่ HEAD `58203b2`)
- `FileAttachmentController` มีด่านแค่ `entityType == "Document"` (`DenyDocAsync`) และมีเฉพาะตอนแนบ/ลบ

  ผลคือสมาชิกทุกคนดาวน์โหลด**สลิปโอนเงินเดือนและใบนำส่ง ปกส. ของรอบเงินเดือน**ได้ถ้ารู้ id (PDPA ม.26) และลบหลักฐานของ JE, การชำระ หรือสินทรัพย์ได้

## ข้อ 30: เพดานพื้นที่เป็นแค่คำเตือน ไม่บล็อก

### ก่อนแก้
- `CanFitStorageAsync` มีผู้เรียกที่เดียวคือ CMS media ซึ่งบล็อก ส่วนเส้นไฟล์แนบไม่เคยเช็คเลย
- counter `Subscription.CurrentStorageUsed` **ไม่มีใครเขียนทั้งเรพ** (`grep` ยืนยัน: ที่ถูกเขียนคือ `CmsSite.CurrentStorageUsed` ซึ่งเป็นคนละตาราง) แต่ยังมีคนอ่านอยู่ 5 จุด ทุกจุดจึงได้ **0 เงียบ ๆ**:

| จุดที่อ่าน | อาการ |
|---|---|
| `GetAggregateUsageAsync.StorageBytes` | หน้าแพ็กเกจกลุ่มโชว์ 0 และด่าน "storage" ของ Account Plan ผ่านเสมอ |
| `CheckUsageLimitAsync("storage")` สายรายบริษัท | ผ่านเสมอ |
| `GetTrialStatusAsync` → `TrialUsageInfo` | หน้า trial โชว์ 0 |
| `AccountSubscriptionController` แยกรายบริษัท | โชว์ 0 |
| `AdminAccountSubscriptionController` แยกรายบริษัท | โชว์ 0 |

### สิ่งที่แก้
- **`Helpers/AttachmentStorageNotice.cs` (ใหม่, pure):** คืนระดับ `Unknown/Ok/Near(≥90%)/Over` พร้อมข้อความไทยที่มีตัวเลข MB จริง ถ้าไม่รู้เพดาน (ไม่มี subscription หรือเพดาน ≤ 0) จะคืน **null** คือไม่เตือน และไม่แต่งเป็น "0 จาก 0"
- **`ISubscriptionService.GetStorageStatusAsync(companyId)` (ใหม่):** คืนการใช้งานจริงของ pool (Σ `FileAttachments.FileSize` + สื่อ CMS) และเพดาน ตอนนี้ `CanFitStorageAsync` เรียกตัวนี้แทน จึงมีสูตรเดียว
- **Upload:** บันทึกไฟล์เสมอ แล้วเรียก `GetStorageStatusAsync` ซึ่งนับแถวที่เพิ่งบันทึกไปแล้ว เพราะคิดจากตาราง ไม่ใช่ counter ที่อาจลืมเขียน ถ้าเกินหรือใกล้เต็มจะตอบ `data.storageWarning` และต่อข้อความท้าย message
- **`api.js`:**
  - `API.upload` เรียก `API.showStorageWarning(res)` ให้อัตโนมัติ ทุกหน้าที่ใช้ `api.uploadAttachment`/`API.upload` จึงได้ toast เตือน (payroll, documents, wht-credit)
  - หน้าที่ใช้ `fetch` ดิบ (`documents.html` flushAttachmentQueue และ `expense.html`) เรียก `API.showStorageWarning(j)` เอง
- **counter ที่ไม่มีใครเขียน:** ทั้ง 5 จุดข้างบนเปลี่ยนไปคิดจากของจริง
  - เพิ่ม `GetStorageBytesByCompanyAsync` สำหรับตัวเลขรายบริษัท
  - ชื่อช่อง JSON `currentStorageUsed` คงเดิม หน้าเว็บไม่ต้องแก้
  - ยังเหลือคนอ่านคอลัมน์นี้ **0 จุด** นอกนิยาม entity
- CMS ยังบล็อกเหมือนเดิม (รูปบนเว็บไม่ใช่หลักฐานบัญชี)

## ข้อ 32: คิวแสดงทุกใบในงวดที่ยังไม่ปิด (ไม่ตัดที่ 30 วันแล้ว)
- **แหล่งความจริงของงวดปิด:** `FiscalPeriod.Status ∈ {Closed, Locked}` และถ้าไม่มีแถวงวดครอบวันนั้นให้ถือว่าเปิด เทียบกันระดับวัน
  - เป็นกติกาเดียวกับ `AccountingService.ValidateFiscalPeriodOpenForDateAsync`, `BankService.EnsureFiscalPeriodOpenAsync` และ `IntegrationService.IsPeriodOpenAsync`
  - ทั้งสามที่เป็น private copy ยังไม่มี helper กลาง ดูหัวข้อ backlog
- **`Helpers/ClosedPeriodRanges.cs` (ใหม่, pure):**
  - `Build` รวมงวดปิดที่ติดกันเป็นช่วงครึ่งเปิด `[Start, EndDate+1วัน)` เพราะ EndDate เก็บเป็นเที่ยงคืนของวันสุดท้าย ถ้าเทียบตรง ๆ เวลา 15:00 ของวันสุดท้ายจะหลุดออกจากงวด
  - `NotInClosed<T>` สร้าง `Expression` ที่ EF แปลเป็น SQL ได้
- **`ActiveLearningRanker`:**
  - นิยาม "อยู่ในคิว" (`QueuedScan`) และ "วันที่ทางบัญชีของสแกน" (`ExtractedDate ?? ProcessedAt ?? CreatedAt`) เป็น static expression **ตัวเดียว** ใช้ทั้ง Rank และ Summarize
  - Rank ใช้ projection เฉพาะช่องที่จำเป็น และมีเพดาน 1,000 ใบกันหน่วยความจำ จำนวนจริงอยู่ใน summary
- **`QueueSummary` (รูปใหม่):** `ClosedPeriodCount · Pending · DraftPending · ScannedInScope · DocumentCreated · JournalOnly · Failed · InProgress · InClosedPeriods`
  - ถอด `WindowDays`, `DocumentStillDraft` และ `OlderPending` ออก ผู้อ่านมีหน้าเดียวซึ่งแก้ในคอมมิตเดียวกัน
  - `InClosedPeriods` คือจำนวนใบที่ยังรอตัดสินแต่วันที่อยู่ในงวดที่ปิดแล้ว หน้าเว็บบอกจำนวนไว้ ไม่ปล่อยให้หายเงียบ
