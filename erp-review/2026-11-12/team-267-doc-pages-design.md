## 0. คำตอบสั้นสำหรับเจ้าของ

- **ลิงก์เดียวต่อใบ** — ต่อยอดลิงก์ชำระของรอบ 241 (ที่ปลอดภัยที่สุดในเรพ: hash + เข้ารหัส + ตรวจสดทุกครั้ง) ให้เป็น "ลิงก์หน้าเอกสาร" ของทุกชนิดที่ลูกค้าเห็นได้ ·
  ลิงก์ยอมรับ/เซ็นรับแบบเดิมหยุดออกใหม่และหมดเองตามอายุ (30/14 วัน) — **ไม่มีระบบลิงก์ที่สอง**
- **หน้าเดียว** — `pages/pay-document.html` (URL ที่อยู่ในอีเมลลูกค้าแล้ว) กลายเป็น "หน้าเอกสาร": หัวใบ · รายการ · ยอด · PDF · ปุ่มตามชนิด/สถานะที่**เซิร์ฟเวอร์ตัดสิน**
  (ยอมรับ/ปฏิเสธ/ขอแก้ · เซ็นรับ · จ่าย/แนบสลิป · ใบเสร็จที่ออกแล้ว · อัปโหลด 50 ทวิ · ผู้ขายรับทราบ PO) · พอร์ทัลลูกค้าเปิดหน้าเดียวกันในโหมดล็อกอิน · การ์ด LINE เปิดหน้าเดียวกัน
- **ผู้ลงนามทุกครั้ง**: ชื่อ · นามสกุล · ตำแหน่ง · ติ๊ก "ข้าพเจ้าเป็นบุคคลของ {ชื่อผู้ซื้อ} และได้รับมอบหมายให้ยืนยันเอกสารนี้" · (ไม่บังคับ) อีเมลรับสำเนา ·
  หลักฐาน ม.9 = เวลา · IP · UA hash · token hash · hash เนื้อหา v2 · hash ไฟล์ PDF ที่เซ็น · แถว audit chain · **ไม่อ้าง ม.26** (ไม่ใช่ลายมือชื่อที่เชื่อถือได้แบบ PKI)
- **ฉบับที่ลูกค้าเซ็น** พิมพ์ชื่อ/ตำแหน่ง/บริษัท/เวลาบนกระดาษทั้ง HTML + QuestPDF แล้วเก็บไฟล์ฉบับนั้น (snapshot + SHA-256) ⇒ ส่งกลับทางช่องที่ลูกค้ามา (อีเมล/LINE) + ดาวน์โหลดบนหน้า
- **หลังจ่าย**: ใช้เส้นเดิมทั้งหมด (gateway/สลิป ⇒ ยืนยัน (รายการเดินบัญชีหรือคน) ⇒ `PostPaymentAutomation` ออก+ส่งใบเสร็จ) + เพิ่ม **ชั้นค่าตั้งต่อใบ** "ออก/ส่งใบเสร็จอัตโนมัติ" +
  หน้าเดียวกันแสดงใบเสร็จที่ออกแล้วให้ดาวน์โหลด · สลิปจากรูปอย่างเดียว**ไม่**ปิดหนี้ (F2 ข้อ 3)
- **ฝั่งพนักงาน**: ปุ่มเดียว "📤 ส่งให้ลูกค้า" (คัดลอกลิงก์ · อีเมล · LINE · QR) + พรีวิวหน้าลูกค้า + ไทม์ไลน์เดียว (ส่งแล้ว → เปิดแล้ว → เซ็น/จ่าย → ใบเสร็จ) — แทน 6 ปุ่มเดิม
- **คำถามที่ต้องให้เจ้าของตอบ** อยู่ใน §18 (ขึ้นต้น ❓) — 9 ข้อ

## 1. หลักคิด

1. **หนึ่งใบ = หนึ่ง token** (ไม่ใช่หนึ่ง token ต่อการกระทำ) · สิทธิ์ของ token = "เป็นผู้ติดต่อของใบนี้" · การกระทำที่ทำได้ **คำนวณสด** ทุกคำขอจากชนิด/สถานะ/ค่าตั้ง (ไม่เก็บ scope ใน token)
2. **Server computes · page displays** (F2 ข้อ 5) — หน้าเว็บไม่มีตารางชนิด/ปุ่ม/ป้าย · ทุกปุ่มมาพร้อม `actionId` + ข้อความ + เหตุที่ทำไม่ได้
3. **ทางเขียนเดิมเท่านั้น** — จ่าย = `PublicPaymentController` เดิม · สลิป = `SlipEvidenceService.SubmitAsync` · ยอมรับ = แกนของ `PublicQuotationController.Accept` (ย้ายเป็น service) ·
   เซ็นรับ = แกนของ `SignDelivery` · ใบเสร็จ = `IssueReceiptForPaymentAsync` ผ่าน `PostPaymentAutomationService` · อีเมล = `SendDocumentRoutedAsync` · LINE = คิว `ContactLineQueueService`
4. **บัญชีหลักฐานเดียว** — ทุกการกระทำของคนนอก (เปิด · ยอมรับ · ปฏิเสธ · ขอแก้ · เซ็นรับ · รับทราบ PO · ส่งสลิป · ส่ง 50 ทวิ) = แถว append-only ในตารางเดียว ·
   คอลัมน์เดิมบนใบ (`QuotationAccept*` · `DeliverySigned*` · `SignLinkOpenedAt`) = **projection** ที่เขียนในธุรกรรมเดียวกัน ⇒ ผู้อ่านเดิม (PDF · Autopilot · ป้าย · webhook) ไม่ต้องแก้
5. **ไม่ประทับสถานะปลายทางเอง** (F2 ข้อ 3) — "ชำระแล้ว" มาจาก gateway/รายการเดินบัญชี/คน · "ส่งแล้ว" = ผู้ให้บริการตอบรับ · "ลูกค้าเปิดแล้ว" = หน้าโหลดจริง (ไม่มี tracking pixel)

## 2. โมเดลลิงก์ (267-1-1 · 267-1-2 · 267-1-3)

### 2.1 token
- ใช้คอลัมน์เดิม `Document.PayLinkTokenHash/PayLinkTokenProtected/PayLinkIssuedAt/PayLinkExpiresAt/PayLinkRevokedAt` (`Document.cs:254-262`) — **ไม่เพิ่มคอลัมน์ token ใหม่** ·
  ชื่อ C# ห่อด้วย record `CustomerDocLink` (อ่าน/เขียนผ่าน service เดียว) · `PayLinkChannelsJson` คงความหมายเดิม (ช่องทางจ่ายของลิงก์)
- ตัวออกเดียว: `DocumentPayLinkService.EnsureLinkAsync` แยกเป็น 2 ชั้น —
  `EnsureCustomerLinkAsync(companyId, docId, purpose)` (ด่าน = `CustomerDocPage.IssueRefusal` §3) และชั้นจ่ายเดิม (ด่าน = `DocumentPayLinkPolicy.IssueRefusal` ตัดสินเฉพาะ action "จ่าย")
  ⇒ ใบเสนอราคา/ใบส่งของ/ใบเสร็จ/CN/ใบวางบิล/PO ออกลิงก์ได้แม้ "จ่ายไม่ได้"
- URL เดิม `{origin}/pages/pay-document.html?c={companyId}&t={token}` (`DocumentPayLinkPolicy.cs:290`) — ลิงก์ชำระที่ลูกค้าถืออยู่ (60 วัน) **กลายเป็นหน้าเอกสารทันที** ไม่ต้อง redirect ·
  ชื่อไฟล์หน้าคงเดิมในรอบนี้ (เปลี่ยนชื่อ = ลิงก์ในอีเมลเก่าเสีย) · คำว่า "pay" ใน path ไม่แสดงต่อผู้ใช้
- **อายุ** (ตาราง OWNER §3 คอลัมน์ TTL): ลิงก์ = `max(อายุ action ที่ยังเปิด, 400 วันสำหรับดาวน์โหลด)` — ตรงกับ `LineDocumentViewLink.TtlDays = 400` · action มีหน้าต่างของตัวเอง
  (เช่น ยอมรับใบเสนอราคาได้ถึง `DueDate` = "ยืนราคาถึง" `DocumentLabels.cs:113-120` + ค่าผ่อนผันบริษัท) · ลิงก์ที่ส่งไปแล้วไม่ถูกทับ (กติกา 259 C-M1 เดิม)
- **ลิงก์เดิม L1/L2** (`QuotationAcceptToken` · `DeliverySignToken` เก็บดิบ): หยุดออกใหม่ตั้งแต่แพ็ก P1 · endpoint เดิมตอบต่อจนหมดอายุ (≤ 30 วัน) · หลังวันหมดอายุสุดท้าย + 7 วัน ⇒
  migration ล้างค่า token ดิบ (`UPDATE … SET QuotationAcceptToken = NULL WHERE expires < now`) แล้วลบ endpoint/หน้าในแพ็กเก็บกวาด · token ดิบที่ยังไม่หมดอายุ ณ วันเปิด P1:
  hash ลงคอลัมน์ `QuotationAcceptTokenHash` (มีอยู่ `:210`) แล้วล้างค่าดิบ ⇒ ฐานไม่มี token ดิบอีก (267-1-3)
- **ลิงก์การ์ด LINE (L4)**: คง HMAC ต่อแถวคิว (เพิกถอนได้รายผู้รับ · ไม่เก็บในฐาน) แต่ปลายทางเปลี่ยนจาก "PDF ตรง" เป็น **หน้าเอกสารในโหมดดูอย่างเดียว + ปุ่มขอทำต่อ** ·
  ถ้าแถวคิวติ๊กลิงก์หน้าเอกสารไว้ (เดิม `IncludePayLink`) การ์ดได้ URL หน้าเอกสารตรง ⇒ ทุกปุ่ม · ไม่ติ๊ก ⇒ L4 = ดู/PDF เท่านั้น (เท่าวันนี้) (267-1-2)
- **แหล่งที่มา (`src`)**: URL ที่ส่งทางอีเมล/LINE ต่อท้าย `&s={hmac(email-log-id|line-queue-id)}` — **ไม่ใช่สิทธิ์** ใช้เพื่อ ① ประทับ "เปิดจากอีเมลถึง x / LINE ของ y" ในไทม์ไลน์
  ② ส่งสำเนาฉบับเซ็นกลับช่องทางเดิม · `s` ผิด/หาย = ไม่มีผลต่อการใช้งาน

## 6. ฉบับที่ลูกค้าเซ็น (renderer ×2 · กฎ #4 A)

- **ข้อมูลบนกระดาษ**: ขยาย `DocumentSigner` ที่ `ResolveSignersAsync` (`PdfGenerationService.cs:1027`) ตั้งให้ slot ลูกค้า: `Name` (ชื่อ นามสกุล) · `Title` (ตำแหน่ง) · `OrgName` · `SignedAt` · `Channel`
  ⇒ HTML `QuotationAcceptanceBlockHtml` (`PdfGenerationService.Stamp.cs:61`) + QuestPDF `ComposeQuotationAcceptanceBlock` (`PdfGenerationService.DocumentRenderer.cs:1233`) **ในคอมมิตเดียว** ·
  ป้ายใหม่ผ่าน `DocumentLabels` เท่านั้น (`SignerTitle` · `SignedOnBehalfOf` · `SignedOnlineEvidenceRef`) · ใบส่งของ slot 1 "ผู้รับของ" เพิ่มตำแหน่ง/บริษัทเช่นกัน · PO ใช้ slot ผู้ขาย
- **บรรทัดหลักฐานท้ายกระดาษ** (เล็ก): "ยืนยันออนไลน์ {วันเวลาไทย} · รหัสอ้างอิง {8 ตัวแรกของ SignedPdfSha256 ของแถวก่อนหน้า/ContentHash}" — ไม่พิมพ์ IP (PDPA)
- **snapshot**: หลังธุรกรรมลงนาม commit ⇒ งาน outbox สร้าง PDF ฉบับนั้นด้วย `GenerateDocumentPdfAsync` เดิม ⇒ เก็บ `IFileStorage` ใต้ `{AttachmentsRoot}/customer-signed/{companyId}/{docId}/{actionId}.pdf`
  (นอก allow-list `/uploads` — แบบเดียวกับรูปลายเซ็น 239) ⇒ ประทับ `SignedPdfPath/Sha256` (แถวหลักฐานได้ "เติม" สองช่องนี้ครั้งเดียว — ข้อยกเว้นเดียวของ append-only ·
  ทำเป็นแถวลูก `CustomerDocumentActionArtifacts` ถ้าผู้ตรวจต้องการ append-only เคร่ง) · ภาษาของ snapshot = `DocumentLanguage` ของใบ (resolver กลาง)
- **ส่งกลับ**: หลัง snapshot สำเร็จ ⇒ (ก) อีเมลถึง `SignerEmail` ถ้ากรอก (ผ่าน `SendDocumentRoutedAsync` โหมดธรรมดา · แนบ snapshot · ผู้ส่งในนามบริษัท `OnBehalfEmailSender` · เพดานเดิม) ·
  (ข) ถ้า `s` ชี้แถวคิว LINE 1:1 ⇒ การ์ด "ฉบับที่ท่านเซ็นแล้ว" (ปุ่มดู = `signed/{actionId}`) · (ค) แจ้งผู้ขาย (เดิม `document.customer_signed`) ·
  snapshot ล้ม ⇒ แถวหลักฐานยังมีผล (การลงนามเกิดแล้ว) + ไทม์ไลน์ "สร้างฉบับเซ็นไม่สำเร็จ · ลองใหม่" + กระดิ่ง (ล้มดัง 3 ที่ · F2 ข้อ 7) · ลูกค้าดาวน์โหลดจากหน้าได้ทันทีหลังสร้างเสร็จ
- เนื้อหาเปลี่ยนหลังเซ็น (Rev ใหม่): ฉบับปัจจุบันไม่พิมพ์ลายเซ็น (`ContentMatches=false` เดิม) · snapshot เก่ายังดาวน์โหลดได้จากหน้าในหัวข้อ "ประวัติ: ท่านยอมรับ Rev.1 เมื่อ …"

   ยังไม่ส่ง = ไม่แสดงป้าย (ไม่อ้างสิ่งที่ยังไม่เกิด) · **ไม่ออกใบเสร็จจากการเปิดหน้า** (ออกเฉพาะจากงานหลังรับชำระ)
3. **สถานะสลิปที่ลูกค้าเห็น**: รอตรวจ (เวลาส่ง · ยอด) → ยืนยันแล้ว (+ ใบเสร็จ) / ปฏิเสธ (เหตุผลที่พนักงานพิมพ์ — ช่องใหม่บน `PaymentIntent` `CustomerVisibleRejectReason`; ไม่พิมพ์ = "ผู้ขายไม่พบยอดโอน กรุณาติดต่อผู้ขาย") ·
   ปฏิเสธแล้วแนบใหม่ได้ (ด่านเดิม "มีรอตรวจแล้ว = ไม่รับ" ใช้กับรอตรวจเท่านั้น)

"ระบบตรวจสลิปเอง" (คำขอเจ้าของ) = **ชั้นที่มีแล้ว** `BankReceiptAutoSettle` (เลขอ้างอิงสลิปที่ลูกค้าแจ้ง = ตัวระบุตัว · statement ของผู้มีสิทธิ์) + **ถอด QR สลิปของแผน 264 P2** (เพิ่มเลขอ้างอิงจาก QR ให้ตัวจับคู่ · ไม่ปิดหนี้เอง) ·
ผู้ให้บริการตรวจสลิปภายนอก = ❓ 267-1-7b (ไม่อยู่ในแพ็กนี้) · หน้าเอกสาร**แสดงผล**อย่างเดียว ไม่ตัดสิน

## 13. ความปลอดภัย

- token 256 บิต · เก็บ hash (SHA-256) + ฉบับเข้ารหัส (`ISecretProtector` · ทะเบียน `SecretReprotectJob` เดิม) · ไม่มี token ดิบในฐานหลังแพ็ก P1 (267-1-3) · ไม่ log URL เต็ม (middleware ตัด `t=`)
- เพดาน (OWNER `CustomerDocPage.Limits` — ตัวเลขเดียว): เปิดหน้า 30/นาที/IP · 300/วัน/token · PDF 10/นาที/IP · respond 5/นาที/IP · 10/วัน/ใบ · สลิป/50 ทวิ ตามเดิม · request-link 1/วัน/ใบ ·
  นับใน `IChatRateLimiter` (DB · หลายเครื่อง) · เกิน = 429 ข้อความเดียว
- anti-enumeration: 404 ข้อความเดียวทุกเหตุ · เวลาเท่ากันโดยประมาณ (โหลดด้วย hash เสมอ) · `relId` ตรวจว่าอยู่ในชุดของใบนั้น (ไม่ใช่แค่บริษัทเดียวกัน)
- XSS: ทุกช่องที่ลูกค้าพิมพ์ (ชื่อ/ตำแหน่ง/เหตุผล/ข้อความ) HtmlEncode ทุก renderer + อีเมลแจ้งผู้ขาย + หน้า staff (กฎ #4 C) · หน้า public ใช้ textContent เท่านั้น
- CSRF: ไม่มี cookie บนเส้น public (token ใน body/query) ⇒ ไม่มีผิว CSRF · โหมด portal ใช้ Bearer เดิม
- การส่งต่อลิงก์: ใครถือลิงก์ก็ลงนามได้ (เหมือน 239) ⇒ ชดเชยด้วยติ๊กรับรอง + แจ้งผู้ขายทันทีพร้อมชื่อ/ตำแหน่ง + ผู้ขายกด "ไม่รับการยอมรับนี้" ได้ (แถว `Voided` อ้างแถวเดิม ·
  projection ล้าง · แจ้งลูกค้า) · step-up OTP อีเมล = ❓ 267-1-6 (ค่าตั้งบริษัท · ยอดเกิน N)
- outbox สำหรับทุกงานเครือข่ายหลังลงนาม (snapshot · อีเมล · LINE · webhook) — คำขอสาธารณะไม่ยิงเครือข่าย
- ไม่มี AI: การตัดสินทั้งหมด pure · ถ้าวันหนึ่งใช้ AI อ่านสลิป/ข้อความ "ขอแก้" ⇒ ผ่าน `IAiOrchestrator` + student + capture (กฎ #1) — ไม่อยู่ในแผนนี้

## 14. LINE Login เติมข้อมูลผู้ลงนาม + PDPA (267-1-13 ❓)

### 14.1 ข้อจำกัดทางเทคนิคที่ต้องรู้ก่อนตัดสิน
- LINE userId **ไม่เหมือนกันข้าม Provider** — ช่อง LINE Login ของ NextAcc (`SiteSettings.LineLoginChannelId` `Models/Entities/SiteSettings.cs:170` · ตัวตรวจ id_token `AuthService.cs:1352`)
  ได้ userId คนละค่ากับ OA ของบริษัทผู้ขาย (`ContactNotifyEndpoint.LineUserId`) เว้นแต่อยู่ Provider เดียวกัน ⇒ **ใช้ LINE Login เพื่อ "จำข้อมูลผู้ลงนาม" ได้ แต่ใช้ผูกปลายทาง OA ของบริษัทไม่ได้**
- LINE ให้ `displayName` (ไม่ใช่ชื่อจริง) + อีเมลเมื่อได้สิทธิ์ ⇒ ไม่เติมชื่อจาก LINE · เติมจาก "สิ่งที่ผู้ลงนามพิมพ์ครั้งก่อนและยินยอมให้จำ"

### 14.2 ดีไซน์
- ปุ่ม "เข้าด้วย LINE เพื่อเติมข้อมูลครั้งหน้า" บนฟอร์มลงนาม (ไม่บังคับ) ⇒ OAuth ช่อง NextAcc (state ผูก token hash ของใบ + nonce) ⇒ ได้ `sub` ⇒ `SubjectKey = HMAC(serverKey, providerId + sub)`
- ตาราง `CustomerSignerProfiles` (TenantEntity — **ต่อบริษัทผู้ขาย** · ไม่แชร์ข้ามบริษัท = จำกัดวัตถุประสงค์): `CompanyId · ContactId · SubjectKey · FirstName · LastName · Title · Email? · ConsentRecordId · LastUsedAt`
- บันทึกเฉพาะเมื่อติ๊ก "จำข้อมูลของฉันสำหรับเอกสารของ {บริษัทผู้ขาย}" ⇒ `PdpaConsentRecord` (`BankAccount.cs:576`) Purpose `customer-signer-prefill` · version · EvidenceHash canonical (system) · Channel `line-login`
- ครั้งหน้า: LINE Login ⇒ เติมช่อง **ผู้ลงนามยังต้องกดติ๊กรับรอง + ยืนยันเองทุกครั้ง** (เติม ≠ ลงนาม) · โปรไฟล์ไม่ใช่หลักฐานตัวตน (แถวหลักฐานบันทึก `SignerProfileId` เพื่ออ้างที่มาเท่านั้น)
- ไม่มี LINE Login: ช่อง "จำบนเครื่องนี้" = `localStorage` ของหน้า (ต่อผู้ชม · ไม่ถึงเซิร์ฟเวอร์ · try/catch) — ค่าตั้งต้นของรอบนี้ ถ้าเจ้าของไม่อยากเปิด LINE Login ฝั่งลูกค้า
- ถอนความยินยอม: ลิงก์ในอีเมลสำเนา + หน้า `my-data`/DSR เดิม ⇒ ลบโปรไฟล์ (แถวหลักฐานการลงนามไม่ถูกลบ — คนละฐานกฎหมาย)

### 14.3 ฐานกฎหมาย PDPA + อายุเก็บ
| ข้อมูล | ฐาน | อายุ |
|---|---|---|
| ชื่อ/ตำแหน่ง/ลายเซ็น/IP/UA hash ในแถวหลักฐาน + snapshot | ม.24(3) สัญญา / ม.24(6) ประโยชน์โดยชอบ (พิสูจน์การตกลง) · ม.24(6)… ภาระตาม พ.ร.บ.บัญชี ม.14 เมื่อใบเป็นเอกสารประกอบบัญชี | `MAX(RetentionUntil ของใบ, วันที่ + 5 ปี)` (กติกา 239 เดิม) · legal hold ⇒ คง |
| โปรไฟล์จำข้อมูล | ม.19 ความยินยอม | จนถอน หรือ 24 เดือนไม่ใช้ (งาน purge กลางคืน · JobLock) |
| Opened (ไม่มี IP) | ม.24(6) | 400 วัน |
- แจ้งเมื่อเก็บ (ม.23): ข้อความสั้นใต้ฟอร์ม + ลิงก์นโยบายของบริษัทผู้ขาย (ค่าตั้งเดิมของ CMS/PDPA) · RoPA (ม.39): แถว `ProcessingActivity` "ลงนามเอกสารออนไลน์" + "จำข้อมูลผู้ลงนาม"
- DSR: access/portability รวมแถวหลักฐาน · erase ⇒ ก่อนพ้นอายุเก็บ = ปฏิเสธพร้อมเหตุ (legal hold) · พ้นแล้ว = `ErasePii` แบบ 239 (ชื่อ→"[ลบตามคำขอ]" · ลบไฟล์ลายเซ็น/snapshot ·
  hash/เวลาคงไว้) · ผู้ลงนามเป็น**บุคคลที่สาม** (พนักงานของลูกค้า) — ตัวหาเจ้าของข้อมูลค้นด้วยชื่อ+อีเมลในแถวหลักฐาน (`PiiAccessLog` ทุกครั้งที่พนักงานเปิดดูหลักฐานเต็ม)

## 20. Litmus ก่อนเริ่ม (ตอบแล้ว)

- **ทางเข้าอื่นที่แตะข้อมูลชุดเดียวกัน**: ลงนาม = หน้าเอกสาร · พอร์ทัล · หน้าเก่า L1/L2 (ช่วงเปลี่ยนผ่าน) · API v1/ExternalApproval · CrossTenant ⇒ ทุกทางเขียนแถวหลักฐาน (ทางเดียว) ·
  จ่าย = เดิมทั้งหมด · ใบเสร็จ = งานหลังรับชำระเท่านั้น
- **เข้มขึ้น ผู้ใช้ทำอะไรแทน**: ชื่อ/นามสกุล/ตำแหน่ง/ติ๊ก บังคับ ⇒ ผู้ไม่ยอมกรอก = "ขอแก้" หรือติดต่อผู้ขาย · ยืนราคาหมด ⇒ ปุ่มขอแก้ยังเปิด · ลิงก์หมด ⇒ ขอลิงก์ใหม่
- **ค่าที่ persist ก่อนแก้**: token ดิบ L1/L2 ⇒ migration (267-1-3) · หลักฐานเก่า 239 ⇒ คงบนคอลัมน์ (ไม่ย้อนสร้างแถวหลักฐาน — ไม่แต่งข้อมูลที่ไม่มี) · ลิงก์ชำระที่ถืออยู่ ⇒ ใช้ต่อ
- **สถานะปลายทางที่ประทับเอง**: ไม่มี — ชำระแล้ว/ส่งแล้ว/ส่ง e-Tax แล้ว มาจากระบบภายนอกหรือคนเท่านั้น
- **kill-switch**: ปิด gateway ทุกตัว ⇒ หน้าเอกสารทำงานครบยกเว้นปุ่มจ่ายออนไลน์ (S37) · ไม่มี AI
- **ไม่ซ้อน**: ไม่มี token ใหม่ · ไม่มีหน้าใหม่ (ต่อยอด pay-document) · ไม่มีเส้นเงินใหม่ · ตารางใหม่ 1 ตาราง (หลักฐาน) แทนการเพิ่มคอลัมน์ 3 ชุด · โปรไฟล์ผู้ลงนามเฉพาะเมื่อเจ้าของเลือก P5

ยังไม่ได้คอมไพล์ในเครื่องนี้ (รายงานอย่างเดียว ไม่มีโค้ด)
