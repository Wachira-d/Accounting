วิธี: อ่านโค้ดอย่างเดียว (ไม่มี SDK · ไม่ได้รันเทสต์) · ทุกข้อชี้ไฟล์:บรรทัดที่เปิดดูแล้ว

## โมเดลความเชื่อถือ (บันทึกตามที่ขอ)

"ที่มา" (`LoadProvenanceAsync`) พิสูจน์ได้แค่ว่า **มีแถว 50 ทวิ ที่ออกแล้วในสมุดของบริษัทผู้จ่าย** และผู้ถูกหักคือผู้ติดต่อของผู้จ่ายที่ผูกกับเรา
มัน**ไม่ได้**พิสูจน์ว่าผู้จ่ายยื่น ภ.ง.ด.53 หรือนำส่งภาษีจริง — ข้อนี้กระดาษก็พิสูจน์ไม่ได้ และการตรวจด้วย AI เดิมก็พิสูจน์ไม่ได้
ถ้าเทียบกับคำตอบ AI แบบ "ดูเหมือนของจริง" ที่มาแข็งกว่า (เป็นแถวจริง ไม่ใช่การเดา) แต่ข้อมูลทุกอย่างในนั้น **ผู้เช่าฝั่งผู้จ่ายเป็นคนพิมพ์เอง** ทั้งหมด
รวมถึง `Company.TaxId` ของผู้จ่ายเองด้วย

ข้อสังเกต: ข้อมูลที่ส่งมาสร้างจากแถวเดียวกับที่ด่านอ่าน (`PartnerWhtCertExchangeService` เป็นผู้สร้าง `NextAccLink` เพียงทางเดียว)
ทุกช่องจึงตรงกันโดยปริยาย ด่านจะล้มก็เฉพาะกรณีแข่งเวลา (ยกเลิก/แก้ใบระหว่างส่ง) หรือแถวกำกวม (F2 ข้อ 6)
สิ่งที่ด่านนี้เพิ่มจริงคือการผูกตัวตน (คู่ค้า Accepted + ผู้ติดต่อผูกเรา) ไม่ใช่การเทียบยอด
ด่านที่กันความเสียหายได้จริงยังเป็นด่านเดิม คือต้องจับคู่ **Exact** กับแถว `WhtCreditReceived` ที่**เรา**บันทึกเอง
ผู้จ่ายจึงสร้างเครดิตขึ้นมาเองไม่ได้ ทำได้แค่ปิดแถวที่เรารออยู่แล้ว — ข้อ M1 คือช่องโหว่ของการปิดแถวนั้น

## HIGH

### H1 — แบทช์ 50 ใบติดค้างถาวร: ใบของคู่ค้าไม่ถูกส่งเลยเมื่อผู้จ่ายมีใบอื่นค้างอยู่ ≥ 50 ใบ
`PartnerWhtCertExchangeService.cs:59-64` (query) · `:105` (`NotPartner ⇒ continue`) · `:107-111` (`Skip ⇒ StampSkipAsync` ไม่นับครั้ง)

- query เลือกใบ 50 ใบที่เก่าที่สุดตาม `IssuedDate` จากใบที่ `PartnerDeliveredAt == null && attempts < 8` **ก่อน**จะดูว่าผู้ถูกหักเป็นใคร
- ใบถึงผู้ขายทั่วไป (`NotPartner`) ไม่ถูกประทับอะไรเลย ส่วนใบที่ถูก `Skip` ประทับแค่เหตุโดยไม่นับครั้ง (ตามคำตัดสิน 264-5-2 ที่ตั้งใจไว้)
- ใบทั้งสองกลุ่มนี้จึงอยู่ในคิวไปตลอด
- สถานการณ์: ผู้จ่ายเปิด `SendWhtCertsToPartners` แล้วออก 50 ทวิ ให้ผู้ขายทั่วไป 50 ใบ (เป็นเรื่องปกติภายในเดือนเดียวของบริษัทขนาดกลาง)
  - ทุกรอบงานหลังจากนั้นจะได้ 50 ใบเดิมกลับมา ใบที่ออกให้คู่ค้าหลังจากนั้นไม่ถูกส่งอีกเลย และไม่มีเหตุแสดงบนใบนั้น (เงียบ)
  - ผลคือคำสัญญา "แก้แล้วรอบถัดไปส่งเอง" ของรอบนี้ไม่เป็นจริง
- ต้นเหตุมีมาตั้งแต่รอบ 255 แต่รอบนี้เพิ่มใบ Skip ที่กินโควตาเข้าไปอีก
- แก้ขั้นต่ำ: กรองผู้ถูกหักใน SQL ก่อน `Take`
  - ให้เหลือเฉพาะ `PayeeContactId ∈` ผู้ติดต่อที่ `ExternalSystem == NextAccTenant` หรือเลขผู้เสียภาษีตรงบริษัทคู่ค้าที่ Accepted
  - หรือใช้ watermark/ตัวชี้ (keyset) ต่อบริษัทแทนการเลือก 50 ใบเก่าสุดซ้ำทุกรอบ
- เทสต์ Db: ออกใบให้ผู้ติดต่อทั่วไป 51 ใบ แล้วออกให้คู่ค้า 1 ใบ ⇒ ใบของคู่ค้าต้องถูกส่ง

## MED

### M1 — ตัวตนผู้จ่ายผูกกับ `Company.TaxId` ที่ผู้เช่ากรอกเอง: คู่ค้าที่ Accepted สวมเลขของลูกค้ารายอื่นของเราแล้วปิดแถวเครดิตของรายนั้นได้ ด้วยความมั่นใจ 1.0
`WhtCertIntakeService.cs:362-365` (`payerIds` = คู่ค้าที่ `TaxId` ตรง `payerTax`) · `CompanyService.cs:285` (เจ้าของบริษัทแก้ `TaxId` ได้โดยไม่มีการยืนยันตัวตน)
· `WhtCertMatchPolicy.cs:63-66` (K1 จับคู่ด้วยเลขผู้จ่ายอย่างเดียว)

- สถานการณ์ — ฝั่งผู้จ่าย:
  - M เป็นคู่ค้า Accepted ของเรา
  - เจ้าของ M เปลี่ยน `Company.TaxId` ของ M เป็นเลขของ X ซึ่งเป็นลูกค้าของเราที่ไม่ได้อยู่บน NextAcc และเรามีแถว "รอ 50 ทวิ" ของ X อยู่
  - M ออก 50 ทวิ ให้ผู้ติดต่อที่ผูกกับเรา โดยใส่ยอดเท่ากับแถวที่เรารออยู่
- สถานการณ์ — ฝั่งเรา:
  - `DeliverForPayerAsync` ส่งเข้ามาโดยใช้ `PayerTaxId` = เลขของ X
  - `LoadProvenanceAsync` หา M เจอ (เพราะเลขตรง) ด่านที่มาไม่มีปัญหา และจับคู่ Exact กับแถวของ X
  - ผลคือ AutoConfirm ขึ้นป้าย "⚙️ ยืนยันจากระบบของผู้จ่าย · แถวตรงทุกช่อง" และ audit `provenance-confirmed`
- ผลกระทบ:
  - แถวเครดิตของ X ถูกปิดด้วยใบที่ X ไม่ได้ออก การทวงใบจริงจาก X หยุดลง
  - ตอนสรรพากรตรวจ ไม่มี 50 ทวิ จาก X ⇒ เครดิตใน ภ.ง.ด.50 ถูกตัด (ม.69 ทวิ)
- ข้อนี้ไม่ได้เพิ่งเกิด เพราะเส้น AI เดิมก็กันไม่ได้ แต่ตอนนี้ระบบประกาศความมั่นใจ 1.0 ด้วยหลักฐานที่ฝ่ายผู้จ่ายคุมทั้งหมด
- แก้ขั้นต่ำ: ผูกตัวตนกับข้อมูลใน**สมุดของเรา** — แถวเครดิตที่จัดสรร (`Candidate.PayerContactId`) ต้องเป็นผู้ติดต่อของเราที่ผูก `NextAccTenant` กับ `ExternalId == id บริษัทต้นทาง`
  - ถ้าไม่ผูก ให้ตั้งด่าน "ผู้จ่ายบนแถวรอใบไม่ได้ผูกกับคู่ค้ารายนี้" (รอคน)
  - อีกทางหนึ่งคือส่ง `PayerCompanyId` มากับข้อมูลที่ส่ง แล้วตรวจให้ตรงกับผู้ติดต่อของแถว
- เทสต์: M เปลี่ยน TaxId เป็นของ X ⇒ ไม่ยืนยันอัตโนมัติ · ทิศตรงข้าม: ผู้ติดต่อผูกถูกต้อง ⇒ ยังยืนยันได้

## ตรวจแล้ว ไม่ใช่บั๊ก

- **Tenant isolation:** query ข้ามบริษัทใน `LoadProvenanceAsync` จำกัดไว้ที่ `payerIds` ที่มาจากคู่ Accepted ของ `companyId` · ผู้ติดต่อต้องเป็นของบริษัทผู้จ่าย (`PayeeContact.CompanyId == w.CompanyId`) และ `ExternalId == companyId.ToString()`
  - รูปแบบเดียวกับที่ `CrossTenantWorkflowService.cs:773/851` เขียน (Guid ตัวเล็ก) ⇒ ไม่มีปัญหาตัวพิมพ์
  - ทั้ง 3 query ของ Autopilot ผูก `CompanyId` · `PartnerPaymentNotices.CompanyId` คือฝั่งผู้ซื้อ (`PartnerPaymentNoticeService.cs:87`)
- **ใบจ่ายบางส่วน:** `Gates` บังคับ `MatchLevel == Exact` (`WhtCertIntakeVerdict.cs:58`) ⇒ Partial เป็นด่าน รอคนเหมือนเดิม และไม่ถาม AI
- **ใบที่ยกเลิก/ออกใหม่:** ยกเลิกก่อนรับ ⇒ ด่าน · ยกเลิกหลังรับ ⇒ `NotifyVoidedAsync` (เดิม) · ใบออกใหม่ ⇒ แถวรอใบถูกปิดไปแล้ว ⇒ NoCandidate/Over ⇒ รอคน (ไม่ได้เครดิตซ้ำ)
- **ปีที่ยื่น ภ.ง.ด.50 แล้ว (รอบ 257):** เส้นที่มายังผ่าน `LockedYearAsync` ทั้งก่อนและใต้ล็อก · ด่านปีภาษีของแถว · ตรวจยอดค้าง/การตัดสูญใต้ล็อก — ไม่ได้ถูกข้าม
