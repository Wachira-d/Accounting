# รอบ 262 — บริษัทผู้ให้บริการเรียกเก็บค่าบริการทาง LINE (LINE OA กลาง = OA ของบริษัทผู้ให้บริการ)

> ปัญหาจากเจ้าของ: "ใช้ LINE OA เรียกเก็บเงินค่าบริการบัญชี เงินเข้าบัญชีของระบบ ควรต้องใช้ได้" — NextAcc (บริษัทผู้ให้บริการ · `SiteSettings.PlatformCompanyId` ·
> ผู้อ่านเดียว `Helpers/PlatformCompanyLookup`) ต้องการส่งใบแจ้งหนี้/ลิงก์ชำระ/ทวงชำระ/ใบเสร็จถึงลูกค้า (ผู้เช่า = ผู้ติดต่อในบริษัทผู้ให้บริการ) ทาง LINE
> และเงินเข้าบัญชีของระบบ · คำตัดสิน: `erp-review/2026-09-29/DECISIONS.md` 262-1-1…262-1-8 · โค้ดตัวตัดสินเดียว `Helpers/ProviderCentralOa.cs`

## 1. สถานะก่อนรอบนี้ (อ่านจากโค้ดจริง)

### 1.1 ทางตันบนหน้าตั้งค่า
- `settings.html` แท็บ LINE บรรทัด "⚙️ ส่งเอกสารถึงผู้ติดต่อทาง LINE … ต้องใช้ LINE OA ของร้านเอง (ตั้งที่ 'ตั้งค่าขั้นสูง' ด้านล่าง)" เป็นข้อความตายตัว แต่ส่วน
  `#lineAdvanced` ถูกซ่อนเมื่อ `isPlatformCompany` (257 C-H1 · 257-1-7) ⇒ บริษัทผู้ให้บริการถูกส่งไปหาส่วนที่ไม่มี (กฎ #4A silent dead end)
- `ContactLineBindingService.CreateInviteAsync` ต้อง `line.CompanyOaReady` (OA ของบริษัท) ⇒ บริษัทผู้ให้บริการ (ตั้ง OA เองไม่ได้) สร้างลิงก์ผูก LINE 1:1 ของผู้ติดต่อไม่ได้เลย
- `ContactRecipientRule.LineGate`: ปลายทาง scope `nextacc` ⇒ กลุ่มเปิดเฉพาะบริษัทผู้ให้บริการ (256-2) แต่ **LINE ผู้ใช้ 1:1 ปิดทุกบริษัท** (`NextAccTenantDeliveryOpen = false` · N8)
- `LineNotifyService.ContactRouteAsync`: scope `nextacc` + ผู้รับ 1:1 ⇒ ปฏิเสธเสมอ (`NextAccNotOpenReason`)

## 2. ทางเลือกการผูก LINE ของผู้เช่ากับผู้ติดต่อในบริษัทผู้ให้บริการ

| ทาง | ผล | ตัดสิน |
| --- | --- | --- |
| A. ให้บริษัทผู้ให้บริการตั้ง OA ตัวที่สองของตัวเอง | ต้องมี OA ใหม่ + ลูกค้าเพิ่มเพื่อนสองตัว · เจ้าของบอกชัดว่า OA ของ NextAcc คือ OA กลาง | ❌ |
| B. ย้าย webhook ของ OA กลางไป URL ของบริษัท | ทุกผู้เช่าพัง (บอท ERP · ลิงก์ลูกค้า · กลุ่ม) — 257-1-7 | ❌ ห้าม |
| **C. OA กลาง = OA ของบริษัทผู้ให้บริการ (เฉพาะบริษัทนั้น) · webhook เดิม `/api/line-webhook`** | คำเชิญ scope `nextacc` · รหัส `ผูก LN-…` ในแชต OA กลาง → webhook กลางค้นเฉพาะคำเชิญของบริษัทผู้ให้บริการ · ส่งด้วย token กลาง · ด่านตัวเดียวกับกลุ่ม 256-2 | ✅ เลือก |
| D. ใช้ `User.LineUserId` ของเจ้าของ (บอท ERP) เป็นปลายทางผู้ติดต่อ | ไม่มีความยินยอมเฉพาะเรื่อง (PDPA ม.19) · ผูกกับคน ไม่ใช่ผู้ติดต่อ · ฝ่ายบัญชีที่ไม่ใช่ผู้ใช้รับไม่ได้ | ❌ (คงเป็นเส้นสำรองข้อความตรงเดิม) |

### 2.1 ตรวจความปลอดภัยของทาง C (หาเหตุปฏิเสธ — ไม่พบเหตุที่หนักพอ)
1. **webhook กลาง** ไม่เปลี่ยน URL/ลายเซ็น (`LineBotService.VerifySignatureAsync`) · ข้อความที่ไม่ใช่รหัส `LN-`/"หยุด" ไม่แตะฐาน (ตรวจรูปแบบก่อนอ่านบริษัทผู้ให้บริการ) ⇒ บอท ERP เดิมได้ข้อความเหมือนเดิม
2. **ข้ามบริษัท**: webhook กลางค้นรหัสด้วย `CompanyId == บริษัทผู้ให้บริการ` เท่านั้น · คำเชิญของบริษัทอื่นไม่มีทางถูกไถ่ (แม้ประทับ scope `nextacc` ด้วยการแก้ฐาน — Db test) ·
   ปลายทาง `nextacc` ของบริษัทอื่นไม่ส่ง (`LineGate` + `CentralContactUserRouteAsync` ตรวจซ้ำตอนส่ง)
3. **ข้าม OA**: คำเชิญมีคอลัมน์ `OaScope` · ไถ่ได้เฉพาะ webhook ของ OA เดียวกัน (`ProviderCentralOa.InviteMatchesChannel`) — userId ของ LINE ใช้ได้เฉพาะ OA ที่ออก
4. **กลุ่มกลางของแอดมิน**: ไม่แตะ (`GroupProblem` ตอนผูก + `IsPlatformCentralGroup` ตอนส่ง) · รอบนี้ไม่เพิ่ม event กลุ่มใหม่ (ใช้เส้น 256-2 เดิม)
5. **บริษัทผู้ให้บริการเปลี่ยน** ⇒ ปลายทางเดิมหยุดส่งทันที (อ่านใหม่ทุกครั้ง) · คำเชิญเดิมไม่ถูกค้น
6. **บอทของ OA กลางเปลี่ยน** ⇒ ปลายทาง `nextacc` ที่ผูกกับบอทเดิม = "ต้องผูกใหม่" (เทียบ `OaDestination` กับ `BotUserId` — ไม่รู้ข้างใด = ไม่ตัดสิน · precedent เดียวกับลิงก์ลูกค้า CMS รอบ 211)
7. **ต้นทุน**: push 1:1 ผ่าน OA กลางเป็นค่าใช้จ่ายของแพลตฟอร์ม (ข้อความของแพลตฟอร์มเอง) ไม่ตัดโควตาผู้เช่า (เหตุผลเดียวกับ 256-2 L5) · ยอด push จริงอ่านจาก LINE (`NextAccOaQuotaWatch`)
8. **ความเสี่ยงที่เหลือ** (บันทึก ไม่ใช่เหตุปฏิเสธ): ผู้ใช้ ERP ที่ผูกบอทกลางและเป็นผู้รับของผู้ติดต่อด้วย พิมพ์ "หยุด" ⇒ ปลดเฉพาะการรับเอกสารของบริษัทผู้ให้บริการ (ไม่ใช่คำสั่ง ERP) — ตรงข้อความยินยอม

## 3. PDPA (ใช้เส้นเดิมทั้งหมด)
- **ม.19 ความยินยอม**: หน้า `contact-line-join.html` เดิม — ผู้รับกดยินยอมเองบนมือถือ → `PdpaConsentRecord` (purpose `ContactLineBindRule.ConsentPurpose` · hash `PdpaConsentEvidence`) ก่อนออกรหัส ·
  ข้อความยินยอมระบุ LY Corporation + บริษัทผู้ส่ง (= บริษัทผู้ให้บริการ) · ปุ่มเพิ่มเพื่อน/ส่งรหัส = Basic ID ของ OA กลาง
- **ม.22/ม.19 ถอน**: พิมพ์ "หยุด" ในแชต OA กลาง ⇒ `TryStopCentralAsync` ปลด + ถอนความยินยอม · unfollow ⇒ ประทับบล็อก · ยกเลิกที่หน้าผู้ติดต่อ (เดิม)
- **ม.39 RoPA**: `EnsureRopaAsync` เดิม (ครั้งแรกที่บริษัทผู้ให้บริการสร้างคำเชิญ)
- **ผู้ควบคุมข้อมูล**: คำเชิญ/ปลายทาง/ความยินยอมอยู่ในบริษัทผู้ให้บริการ (ผู้ส่งเอกสาร) แม้ผู้เช่ากดขอลิงก์เองจากศูนย์บิล (audit ระบุผู้ขอ)
- **ส่งน้อยที่สุด**: การ์ดเดิม (`LineDocumentCard` — ไม่มีเลขผู้เสียภาษี/ที่อยู่) · กลุ่ม "ซ่อนยอด" ไม่มีปุ่มชำระ/ดู PDF (เดิม)
- กลุ่ม: ใช้เส้นรับรองสิทธิ์สมาชิก (`contact-line-group-attest`) รอบ 254/256 เดิม — ไม่เปลี่ยน

## 4. สิ่งที่สร้างรอบนี้
1. ตัวตัดสินเดียว `Helpers/ProviderCentralOa` (pure) + `LineOpenness.NextAccUserOpen/CentralOaDestination` · `LineGate` เปิด 1:1 `nextacc` เฉพาะบริษัทผู้ให้บริการ
2. ผูก: `CreateInviteAsync` (บริษัทผู้ให้บริการ ⇒ scope `nextacc` ต้อง OA กลางมี token+secret) · `ConsentAsync` (ตรวจ OA กลาง/บอท) · `TryRedeemAsync(oaScope)` ·
   ทางเข้า webhook กลาง `TryRedeemCentralAsync`/`TryStopCentralAsync`/`SetBlockedCentralAsync` (ต่อสายใน `LineWebhookController` ก่อนบอท ERP)
3. ผู้เช่าผูกเอง: ศูนย์บิล `GET/POST api/subscription/{companyId}/billing-center/line|line-invite` (Billing.Manage · ปฏิเสธคีย์ API) → คำเชิญของผู้ติดต่อของตนในบริษัทผู้ให้บริการ
4. ส่ง: `LineNotifyService.CentralContactUserRouteAsync` (token กลาง · ตรวจบริษัทผู้ให้บริการตอนส่ง) · ด่านบันทึกกฎตารางส่ง `centralUserOpen`
5. การแจ้งค่าบริการ → คิว LINE ของผู้ติดต่อ: `PlatformBillingNotifier.QueueContactCardsAsync` (ใบใหม่ · ทวงทุกขั้น) + `ReceiptIssuedAsync` (ซื้อตรง + ตัดชำระใบแจ้งหนี้) ·
   ช่องเดียว: เจ้าของที่ LINE id ตรงปลายทางที่ได้การ์ดแล้วไม่ได้ข้อความตรงซ้ำ · ปลายทางที่ได้การ์ด trigger เดียวกันจากกฎตารางส่งแล้วไม่เข้าคิวซ้ำ · แถวจอง `line-contact` = `Queued` (ไม่ใช่ "ส่งแล้ว")
6. ปุ่มชำระของการ์ดใบค่าบริการ = **ศูนย์บิลของผู้เช่า** (`/pages/billing.html` — เส้นชำระของแพลตฟอร์ม: เงินเข้าบัญชีของระบบ · ต่ออายุผ่าน `SubscriptionPayment`) ไม่ใช่ลิงก์ชำระเอกสารทั่วไป
7. ชั่วโมงเงียบ/กระดิ่งล้ม/ถอดรหัสไม่ได้ (260-4): ผ่าน `ContactLineQueueService` ตัวเดิม (OA กลางล้ม ⇒ กระดิ่งผู้ดูแลระบบ) · ใบเสร็จหลังผู้เช่าจ่าย = `CustomerInitiated` (ไม่รอช่วงเงียบ)
8. `settings.html`: ประโยคจากเซิร์ฟเวอร์ (`ContactSendNotice` — ไม่อ้างส่วนที่ซ่อน) + แถวความพร้อม `ProviderLineReadiness` (OA กลาง · Basic ID · webhook · ลูกค้าที่ผูกแล้ว · สวิตช์ LINE ของการเรียกเก็บ)

## 5. ยังไม่ทำ (ตั้งใจ)
- ผลตัดบัตรอัตโนมัติ/ระงับระดับบริษัท: คงเป็นข้อความตรงถึงเจ้าของ (เรื่องบัญชี/บัตร ไม่ใช่เอกสาร — ไม่มีการ์ดให้)
- ใบเสร็จส่วนเสริม/โควตาเสริม (`IssueAddOnReceiptAsync`) ยังไม่เข้าคิว LINE — งานถัดไป (ต่อสายเดียว `ReceiptIssuedAsync`)
- ลิงก์ชำระสาธารณะ (`pay-link.html?t=`) ในการ์ด: token แสดงครั้งเดียว (เก็บ hash) ⇒ คิวที่ลองใหม่ต้องได้ URL เดิม — ต้องออกแบบที่เก็บ URL ในคิวก่อน · รอบนี้ปุ่ม = ศูนย์บิล (ต้องล็อกอิน)
- กฎตารางส่ง/ส่งเองจากหน้าเอกสารของบริษัทผู้ให้บริการ ยังออก **ลิงก์ชำระทั่วไป** ให้ใบค่าบริการทางอีเมลได้ (การ์ด LINE ถูกบังคับไปศูนย์บิลแล้ว) — ฝ่ายค้านควรโจมตีจุดนี้
