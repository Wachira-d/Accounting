## HIGH

### H1 — ฟอร์มแก้ไขส่ง `Guid.Empty` (= ล้าง) เมื่อค่ายังไม่ถูกเติม ⇒ ถอดใบต้นทางของใบเสร็จร่างเงียบ ๆ
- ที่: `Accounting/wwwroot/pages/documents.html:10048-10050` (payload) · `:7273-7306` (`_loadReceiptSourceDocs`) · `:7253` (จุดเดียวที่ตั้ง `_receiptSourceId = rid`)
- กลไก: ตอนแก้ไขใบเสร็จร่าง payload ส่ง `relatedDocumentId: this._receiptSourceId || '0000…'` **ทุกครั้ง** ·
  `_receiptSourceId` ถูกตั้งเป็น `null` ที่ต้น `_loadReceiptSourceDocs` (`:7280`) และกลับเป็นเลขใบต้นทางก็ต่อเมื่อ `_applyPinnedSource` ถูกเรียก (`:7306`) ·
  มี 3 ทางที่ออกก่อนถึงบรรทัดนั้น: `section.style.display === 'none'` (`:7276`) · ไม่มี `contactId` (`:7283`) · ไม่มี `api` (`:7284`) ·
  และระหว่างรอ `getDocuments` (async) ค่าก็เป็น `null` อยู่
- เคสพัง: ใบเสร็จร่างที่ **แปลงมาจากใบแจ้งหนี้** (เส้นที่ใช้บ่อยที่สุด · `CanChangeReceiptSource = true` เพราะเป็น DraftReceipt) → เปิดแก้ไข →
  กดบันทึกก่อนลิสต์ใบค้างโหลดเสร็จ หรือฟอร์มอยู่ในสภาพที่ส่วน "รับชำระใบค้าง" ถูกซ่อน → เซิร์ฟเวอร์ได้ `Guid.Empty` →
  `ApplyReceiptSourceOnUpdateAsync` ล้าง `RelatedDocumentId` (มีแถว audit `ClearDraftReceiptSource` แต่ผู้ใช้ไม่เห็นอะไร) →
  อนุมัติ = ขายสด (Dr เงิน / Cr รายได้ + ภาษีขาย) ทั้งที่ใบแจ้งหนี้ลงรายได้ไปแล้ว และลูกหนี้ไม่ถูกตัด ·
  ด่านเดิม "ใบเสร็จลอยที่มี VAT" (`DocumentService.cs` ~`:7141`) ช่วยได้เฉพาะใบที่มี VAT และลูกค้ายังมีใบค้าง
- ก่อนรอบนี้ไม่มีทางเกิด (update ไม่รับ `RelatedDocumentId`) ⇒ เป็นการถดถอยที่รอบนี้เพิ่ม
- แก้ขั้นต่ำ: ส่ง `relatedDocumentId` เฉพาะเมื่อ (ก) hydrate เสร็จแล้ว และ (ข) ค่าต่างจาก `_pinnedSourceId` ·
  ส่ง `Guid.Empty` เฉพาะเมื่อผู้ใช้ **เลือก** "ใบเสร็จอิสระ" เอง (ธง `userTouched` ที่ `onReceiptSourceSelect`) — "ไม่ได้ตรวจ" ต้องไม่เท่ากับ "ล้าง" (F2 ข้อ 5)

## MED

  และ `Document.Status` ไม่ใช่ concurrency token (`AccountingDbContext` มี token เฉพาะตารางอื่น)
- เคสพัง: คำขอ ก (แก้ไข) โหลดใบเสร็จร่าง → คำขอ ข (อนุมัติ) commit: ออกเลข + ลง JE แบบขายสด → คำขอ ก ผ่าน `Classify == DraftReceipt` (ค่าที่โหลดไว้ก่อน)

  ผล: ใบที่ออกเลขแล้วพิมพ์หัว/อ้างใบต้นทางใหม่ (`PdfGenerationService` อ่านค่านี้) · JE เป็นขายสด · ใบแจ้งหนี้ไม่ถูกตัด = สิ่งที่ 266-1-2 ห้าม
- เส้นปุ่มผูก (`ReceiptLinkService.cs:337-352`) ล็อกสองแถวแล้วตัดสินซ้ำ — เส้นฟอร์มไม่ทำ (ทางเข้าที่สองของข้อมูลชุดเดียวกัน · F2 ข้อ 1)

  3. สร้างใบเสร็จผ่าน API อ้างใบแจ้งหนี้ **ร่าง** / ใบกำกับขายเงินสด (`IssuedAsCashReceipt`) ของผู้ติดต่อเดียวกัน — G-1 ตอนสร้างผ่าน (ตรวจแค่ชนิด/ผู้ติดต่อ/สกุล)
     ทั้งที่ปุ่มผูกปฏิเสธด้วย `RL-DRAFT-TARGET` / `RL-SERVED-AS-RECEIPT`
- พรีวิวเขียนตรง ๆ ว่าตรวจซ้ำ "ผู้ติดต่อ/ยอดค้าง/ภาษีถูกหัก" (`ReceiptLinkPolicy.cs:343`) จึงไม่โกหก แต่ทางเข้าสร้าง/แก้ไข/อนุมัติเดินด่านคนละชุดกับปุ่ม
- แก้ขั้นต่ำ: ใน `GuardReceiptSourceAsync` เมื่อใบเป็นใบเสร็จสร้างเอง (ไม่ใช่ settlement/มัดจำ) และใบต้นทางอยู่ใน `TargetTypes` ให้เรียกส่วนฝั่งใบปลายทางของ `Decide`
  (สถานะ · ถูกแทน · `ServesAsReceipt` · `PartialRefusal`) ตอนอนุมัติ — ต้องมีเทสต์ทิศตรงข้ามว่าใบเสร็จที่แปลงจากใบเสนอราคา/ใบวางบิลยังอนุมัติได้

## ตรวจแล้วไม่พบปัญหา

- **ทางเขียน `RelatedDocumentId` ของใบเสร็จที่ออกเลขแล้ว:** ผู้เขียนทั้งเรพ = สร้าง · แปลง · ใบเสร็จอัตโนมัติ · บริการผูก (ล็อก + ตัดสินซ้ำ) · ฟอร์มแก้ไข (ด่าน `Classify`) ·
  ปุ่ม "ผูกกับเอกสารต้นทาง" เดิม (`DocumentService.Link.cs`) รับเฉพาะใบแจ้งหนี้/ใบกำกับ/ใบแจ้งหนี้ซื้อเป็นใบลูก · `UpdateDocumentAsync` รับเฉพาะร่าง/ถูกตีกลับ (ใบเสร็จไม่อยู่ใน `RevisableTypes`) — เหลือช่องเดียวคือการแข่ง M1
- **ทางเลี่ยง G-1:** แปลง · โคลน · รายการประจำ · นำเข้า · ร่างจากคู่ค้า เดินผ่าน `CreateDocumentAsync` (ด่านตอนสร้าง) และ `ApproveDocumentAsync` (ด่านซ้ำ) · เปลี่ยนผู้ติดต่อของใบร่างที่ผูกอยู่ถูกจับที่ update
- **เงินรอจัดสรร:** กดซ้ำ/สองแท็บถูกจับใต้ล็อกด้วย `ExpectedUnappliedBefore` · ถอดผ่านเส้นเดิม (กลับ JE · คืนยอด · งวดยื่นแล้วปฏิเสธ) · สิทธิ์เท่าหน้าเงินรอจัดสรร (Approve / Void ของชนิดใบปลายทาง)
- **Tenant isolation:** ทุก query ใหม่มี `CompanyId` รวม raw SQL `FOR UPDATE`
- **รั่วข้ามผู้ติดต่อ:** ผู้สมัครทุกชุดกรอง `ContactId` เดียวกับใบที่เปิด + ชั้นความลับ
- **XSS:** ข้อความจากเซิร์ฟเวอร์ทุกจุดผ่าน `Layout.esc` · หัวกล่องใช้ `textContent` · Id ใน `onclick` ผ่าน `Layout.jsArg`
- **งวดปิด/ยื่นแล้ว:** เส้นใบร่างไม่มี JE · สองเส้นเงินใช้ด่านงวดของเส้นเดิม (พรีวิวไม่ตรวจวันที่ ⇒ ปฏิเสธตอนยืนยัน แบบดัง)
- **หัวกระดาษของใบแจ้งหนี้ปลายทาง:** ใบปลายทางต้องมียอดค้าง ⇒ ยังไม่ถูกยกหัวเป็นใบเสร็จ (`ComputeServedAsReceipt`) ตอนผูก
