## 0. คำตอบสั้นสำหรับเจ้าของ

**ยังไม่ได้** — วันนี้ไม่มีทางใดที่ผู้ใช้จะเอา "ใบเสร็จรับเงินที่ออกเลขแล้ว (REC003)" ไปผูกกับ "ใบแจ้งหนี้ที่มีอยู่แล้ว (INV001)" ไม่ว่าจากหน้าใบแจ้งหนี้หรือหน้าใบเสร็จ
และตัวตัดสินการผูกภายหลังที่มีอยู่ (`Helpers/DocumentLinkPolicy.cs:13` — คำตัดสินข้อ 139) **ห้ามผูกใบรับเงินโดยเจตนา** ("หลายรายงานตีความ 'ไม่มีต้นทาง' = ขายสด")

สิ่งที่ "เลือกผูกเองได้" แล้ววันนี้ (ทุกทางบังคับเจ้าเดียวกัน ยกเว้นข้อ 1 ที่บังคับแค่ฝั่งหน้าจอ):
1. **ใบเสร็จฉบับร่าง → ใบค้างชำระ** — ตอน*สร้าง*ใบเสร็จ เลือก "รับชำระใบค้างของลูกค้า" ได้ (`documents.html:7261–7300` → payload `relatedDocumentId` `:10027`) · บันทึกแล้ว**ล็อก**
   ("เปลี่ยนใบต้นทางที่นี่ไม่ได้ … ยกเลิกใบนี้แล้วสร้างใหม่" `:7255`) · `UpdateDocumentRequest` (`DocumentDtos.cs:264`) ไม่มีช่อง `RelatedDocumentId`
2. **ใบแจ้งหนี้/ใบกำกับ ↔ ใบเสนอราคา/ใบส่งของ** และ **ใบแจ้งหนี้ซื้อร่าง ↔ ใบรับสินค้า** (`DocumentService.Link.cs` · ข้อ 139) — ไม่ใช่ใบเสร็จ
3. **เงินรอจัดสรร (21630) → ใบค้าง** (`CustomerCreditService.AllocateAsync` `:279` · ปุ่ม "🧩 ใช้เงินรอจัดสรร" บนใบ `documents.html:13408`)
4. **ใบมัดจำ → ใบแจ้งหนี้** ("หักมัดจำ" `ApplyDepositToInvoiceAsync` `DocumentService.cs:6013`)

ความต้องการของเจ้าของ**ทำได้** แต่ "ผูก" ไม่ใช่การกระทำเดียว — ขึ้นกับว่า REC003 *คืออะไร* (§2) · ข้อเสนอ: บริการผูก/ถอดตัวเดียว + ตัวตัดสินตัวเดียวที่จัดชนิด REC003
แล้ว **ส่งต่อไปเส้นที่ถูกต้องตามกฎหมาย** (บางชนิด = ย้ายเงินได้ · บางชนิด = ต้องยกเลิกแล้วออกใบแทน · บางชนิด = ไม่ใช่การผูกแต่เป็น "ใบซ้ำ" ต้องเลือกยกเลิกใบหนึ่ง) พร้อมพรีวิวผลก่อนยืนยัน (§4)

## 2. "ผูก" ต้องหมายถึงอะไร — แยกตามชนิดของ REC003 + ผลกฎหมาย/บัญชี

หลักตั้ง: การผูกมี **2 ชั้น** ที่ต้องแยกกันเสมอ
- **ชั้นเงิน** — เงินก้อนนี้ล้างลูกหนี้ใบไหน (JE · `BalanceDue` · `PaymentAllocation` · ภาษีถึงกำหนด) → *ย้ายได้* ภายใต้ด่านงวด/ภาษี
- **ชั้นกระดาษ** — ใบเสร็จที่ออกเลขแล้วพิมพ์ว่าอะไร (เลข · วันที่ · ยอด · ใบที่อ้าง · บทบาทใบกำกับ) → **ห้ามแก้** (§86/4 · ม.105 · เลขรันไม่ขาด) ·
  ถ้ากระดาษพูดผิดหลังย้ายเงิน = **ยกเลิกแล้วออกใบแทน** (กลไก §2.4c) หรือ**ปฏิเสธ** เมื่อยกเลิกไม่ได้ (ถึงกรมสรรพากร/รายงานล็อก)

### 2a. ใบเสร็จที่ออกให้เงินรอจัดสรร/มัดจำ/ใบอื่น → จัดสรรใหม่ (JE · 21630 · ลูกหนี้)
- **R1** JE: `Dr 21630 / Cr ลูกหนี้(INV001)` อ้าง `{เลขการชำระ}/A{n}` (สูตรเดิม `AllocateAsync`) · ภาษี: `LateReceiptTaxPoint.Decide(เหตุผลของเงิน, …)` — เงิน "ค้างออกใบ" ⇒ งวด VAT = เดือนรับเงิน (258-1-5 · 260-5-1/5) ·
  ภาษีถูกหักปิดยอดครบ ⇒ Dr 11910 / Cr ลูกหนี้ (258-1-17) · ไม่มีใบเสร็จใหม่เพราะ REC003 คือใบรับของเงินก้อนนี้ (ต้องให้ `ManualReceiptCoverage`/ตัวออกใบเสร็จรายใบนับ REC003 เป็น "มีแล้ว" — ไม่งั้น `TryAutoIssueAllocationReceiptAsync` ออกใบที่สอง)
- **R3/R4** ขาเงินสด**ไม่ขยับ** — ถ้าเปลี่ยนด้วย "ยกเลิกการชำระ แล้วบันทึกใหม่" (ทางเดียววันนี้) JE เงินสดถูกกลับ+ลงใหม่ ⇒ **คู่จับคู่ธนาคารหลุด** (DOCUMENT_FLOW §6.0c) + เลขการชำระใหม่ + ใบเสร็จอัตโนมัติถูกยกเลิก ·
  ข้อเสนอ (266-1-3): ย้ายผ่านผังพัก **สองขาอ้างเลขการชำระเดิม** — `Dr ลูกหนี้(INV002) / Cr 21630` (`{เลข}/M{n}-OUT`) แล้ว `Dr 21630 / Cr ลูกหนี้(INV001)` (`{เลข}/M{n}-IN`) ในธุรกรรมเดียว ⇒ บรรทัดเงินสดและคู่ธนาคารคงเดิม · audit อ่านได้ว่า "ย้าย" ไม่ใช่ "รับใหม่"
  (ผังลูกหนี้ของแต่ละใบอ่านจาก `OriginalArApAccount` — ห้ามเดา) · INV002 กลับไปค้าง · INV001 ลดค้าง
- ภาษีของ INV002 (บริการ · VAT พัก 21913 ที่ถูกย้ายเข้า 21911 ตอนรับเงิน): ถอนเงินออก ⇒ ต้องถอยภาษีขายถึงกำหนด (`UndoOutputVatOnPaymentVoidAsync` ตัวเดียวกับยกเลิกการชำระ) — **งวดยื่น/ล็อกแล้ว = ปฏิเสธทั้งรายการ**
- ภาษีของ INV001: เงินนี้เป็นค่าของ INV001 ตั้งแต่วันรับ ⇒ จุดความรับผิด = **วันรับเงินเดิม** (ตรรกะ "ค้างออกใบ" ของ `LateReceiptTaxPoint`) · งวดนั้นยื่นแล้ว ⇒ งวดปัจจุบัน + ธง `[DEPOSIT-LATE-VAT]` (ทางเดียวกับ 258-1-5) + แจ้งเรื่องเบี้ยปรับ/เงินเพิ่ม

### 2b. ใบเสร็จที่ข้อความบนกระดาษอ้างใบอื่น หรือไม่อ้างใบใด — กระดาษเปลี่ยนได้ไหม
- **เปลี่ยนไม่ได้** — ใบที่ออกเลขแล้ว (Approved/Paid/Sent) แก้ `Reference`/บรรทัด/หัวไม่ได้ (§86/4 · ม.105 · DOCUMENT_FLOW §1.3) · ข้อ 139 จงใจไม่แตะ `Reference` ด้วยเหตุผลเดียวกัน
- **ระวังผลข้างเคียงที่ซ่อนอยู่**: หัวกระดาษ*คำนวณตอนพิมพ์* จาก `RelatedDocumentId` — `HasSeparateReceiptAsync` (`PdfGenerationService.cs:1909`) ทำให้ใบกำกับ INV001 ที่เคยพิมพ์ "…/ใบเสร็จรับเงิน" (รับเงินวันเดียวกัน) **เปลี่ยนหัวเมื่อพิมพ์ซ้ำ** ถ้ามีใบเสร็จมาผูกภายหลัง ·
  `SettlesTaxInvoiceSource` เปลี่ยนข้อความของใบเสร็จตามชนิดใบต้นทาง ⇒ **ห้ามเขียน `RelatedDocumentId` ของใบเสร็จที่ออกเลขแล้ว** (266-1-2) — ชั้นข้อมูลของการผูกภายหลังต้องอยู่ที่แถวเงิน (`PaymentAllocation`) ไม่ใช่ที่ FK ที่ renderer อ่าน
- ทางเลือกตามสภาพกระดาษ:
  1. **กระดาษไม่อ้างใบใด** (R1 ใบเสร็จเงินเครดิตของ 265 · ใบเสร็จที่บรรทัดเป็น "รับเงินล่วงหน้า/ตามยอดค้าง") ⇒ ผูกชั้นเงินอย่างเดียว ไม่แก้กระดาษ + ออก **"ใบแจ้งการนำเงินไปตัดชำระ"** (Payment application advice — เอกสารแจ้ง ไม่ใช่ใบรับ/ใบกำกับ · ไม่มีเลขชุดภาษี · ไม่เข้า ภ.พ.30) ให้ลูกค้าได้ถ้าต้องการ (266-1-6)
  2. **กระดาษอ้าง INV002** (R3/R4) ⇒ ข้อความบนใบรับเป็นเท็จหลังย้าย ⇒ **ยกเลิก REC003 + ออกใบแทน** ผ่านตัวสร้างตัวเดียว `CreateSettlementReceiptAsync` (`:14978`) ลง**วันที่รับเงินเดิม** (ม.105 · 260-5-1) ·
     `ReplacesDocumentId=REC003` · เหตุผลบังคับ · เลขใหม่จากเล่มตามบทบาท (`TaxInvoiceSeriesPolicy`) · REC003 คงสถานะ Voided (ห้ามลบ · §87/3)
  3. **ยกเลิกไม่ได้** (e-Tax ถึงกรมสรรพากร `EtaxReachedRdStatuses` `DocumentVoidPreconditions.cs:91` · อยู่ในรายงานภาษีที่ล็อก · งวดบัญชีปิด) ⇒ **ปฏิเสธการย้าย** พร้อมทางไปต่อ ("ติดต่อผู้ทำบัญชี — ใบนี้ถึงกรมสรรพากรแล้ว · ใช้ใบลดหนี้/ใบเพิ่มหนี้ในงวดปัจจุบัน") — ห้ามย้ายเงินแล้วปล่อยกระดาษอ้างผิด
- "หมายเหตุอ้างอิงเพิ่ม" บนใบเดิม = **ไม่แนะนำ** สำหรับส่วนที่พิมพ์ (กระดาษที่ลูกค้าถือกับที่ระบบพิมพ์ซ้ำจะต่างกัน) · ใช้ได้เฉพาะ `InternalNotes` (ไม่พิมพ์) เพื่อผู้ตรวจสอบ

### 2c. บทบาทใบกำกับภาษี vs ใบเสร็จ · VAT ที่รายงานแล้ว · tax point
- **ใบแจ้งหนี้สินค้า/ใบกำกับภาษี** = VAT เข้า 21911 ตอนออก · ใบเสร็จของการรับชำระ = ใบเสร็จเปล่า VAT=0 (`CreateSettlementReceiptAsync` `:15060`) ⇒ ย้ายเงินไม่กระทบ ภ.พ.30
- **ใบแจ้งหนี้บริการ** (VAT พัก 21913) = ใบเสร็จที่ปิดเต็มใบ**ถือ VAT** (ใบกำกับ ณ วันรับเงิน §78/1 · `carryVatFromSource`) ⇒ ใบเสร็จนั้นคือใบกำกับภาษี — ย้าย = ยกเลิกใบกำกับ + ออกใบใหม่ (§86/4 · กฎ A "ห้ามแก้ไขย้อนหลัง") · งวด ภ.พ.30 ของใบเดิมยื่นแล้ว ⇒ **ปฏิเสธ**
- **R5/R6 ใบขายสดที่ซ้ำกับ INV001**: ใบกำกับสองใบต่อการขายเดียว ⇒ VAT ขายเบิ้ลใน ภ.พ.30 · ผู้ซื้อเคลมภาษีซื้อได้สองครั้ง · สต็อกตัดสองรอบ ⇒ ต้องเลือก "ใบไหนคือของจริง" (ใบที่ลูกค้าใช้เคลมภาษีซื้อคงไว้):
  - คง REC003 (ขายสด) → **ยกเลิก INV001** (ถ้ายกเลิกได้) หรือ**ใบลดหนี้เต็มใบ** อ้าง INV001 ในงวดปัจจุบัน (§86/10 · ถ้าใบแจ้งหนี้ยื่น ภ.พ.30 แล้ว)
  - คง INV001 → **ยกเลิก REC003** (ถ้ายกเลิกได้ — กลับรายได้/VAT/สต็อก) แล้ว**บันทึกรับชำระ INV001 ลงวันที่ REC003** (ใบเสร็จอัตโนมัติใหม่ลงวันที่รับเงินจริง) · ยกเลิกไม่ได้ ⇒ ใบลดหนี้อ้าง REC003 (ใบเสร็จ/ใบกำกับ) + บันทึกรับชำระด้วยเงิน… ซึ่งเงินอยู่ที่ REC003 แล้ว ⇒ เคสนี้**ให้คนตัดสิน** (ผู้ทำบัญชี) ไม่อัตโนมัติ
  - การ "แปลง REC003 จากขายสดเป็นใบรับชำระ INV001 ในที่" (สลับ Cr รายได้/VAT เป็น Cr ลูกหนี้) = เปลี่ยนความหมายทางภาษีของใบกำกับที่ออกแล้ว + ภ.พ.30 ที่อาจยื่นแล้ว ⇒ **ไม่ทำ** (266-1-5)
- tax point (§78/§78/1): วันรับเงินจริง = วันที่บน REC003 — ไม่เปลี่ยนเพราะการผูก · ผลต่อ INV001 = `LateReceiptTaxPoint` · INV002 (ถ้าถอนเงิน) = ถอยภาษีถึงกำหนด

### 2d. ยอดไม่ตรง · บางส่วน · เกิน · WHT · หลายต่อหนึ่ง/หนึ่งต่อหลาย
- **ยอด REC003 = ยอดค้าง INV001** — ปิดยอด · สถานะผ่าน `DocumentSettlementState.Apply`
- **น้อยกว่า** = รับบางส่วน · INV001 มี VAT พัก (ใบแจ้งหนี้บริการ) ⇒ **ปฏิเสธ** `RD-78/1-PARTIAL-VAT-INVOICE` (`VatInvoiceSettlementGate.PartialRefusal` · 258-1-23) พร้อมทางไปต่อ (แปลงเป็นใบกำกับก่อน/ปิดเต็มยอด)
- **มากกว่า** = ส่วนเกินเป็นเงินรอจัดสรร**ต้องมีเหตุผล** (`PaymentExcessPlan` · 258-1-2/3) — ห้ามจ่ายเกินใบ (`DocumentSettlementState.WouldOverpay`)
- **WHT ฝั่งขาย** (ลูกค้าหักเรา): ภาษีถูกหักอยู่บนการชำระ/แถวจัดสรร (Dr 11910) — ย้ายเงิน = ย้าย WHT ตาม (แถวจัดสรร `WithholdingTaxAmount`) · ด่านเพดานสะสมต่อใบ (สูตรเดียวกับ `:12660–12685`) ·
  เกณฑ์เงินสด: ใบแจ้งหนี้ตั้งลูกหนี้ gross ⇒ ปิดยอดครบแต่ WHT ไม่ครบ = ลูกหนี้ค้างใน GL (ด่าน `:12697` เดิม) · 50 ทวิ ขาเข้า (§2.12j) ที่ผูกกับ INV002 ต้องย้ายตาม หรือติดป้าย "50 ทวิ ต้องตรวจ" (ระบบไม่เดา)
- **หลายใบเสร็จ ↔ ใบแจ้งหนี้เดียว** = งวดผ่อน — ได้ (แต่ละใบเสร็จ = เงินคนละก้อน) ภายใต้ด่านบางส่วนข้างบน
- **ใบเสร็จเดียว ↔ หลายใบแจ้งหนี้** = เงินก้อนเดียวจัดสรรหลายใบ — ชั้นเงินมีแล้ว (`CreateMultiDocPaymentAsync`/`AllocateAsync`) · ชั้นกระดาษ = ใบเสร็จรายใบ (258-1-6/20) หรือใบเสร็จรวม (**265**) · การย้าย*ชิ้นหนึ่ง*ของใบรวม = ออกใบรวมใหม่ทั้งใบ ⇒ v1 ปฏิเสธ (R7)

### 2e. เจ้าเดียวกัน — สาขา · สำนักงานใหญ่ · การรวมผู้ติดต่อ
- คีย์ผู้ติดต่อ = **เลขผู้เสียภาษี + สาขา** (DOCUMENT_FLOW §6.2i · คำตัดสิน #20) ⇒ สำนักงานใหญ่กับสาขาเป็น**คนละแถว** · ใบเสร็จพิมพ์ชื่อ/สาขาผู้ซื้อ (§86/4(3) · ประกาศ 199) ⇒ ผูก REC003 (สาขา 00001) กับ INV001 (00000) =
  กระดาษสองใบระบุผู้ซื้อคนละสาขา ⇒ **ปฏิเสธ** (266-1-4) พร้อมทางไปต่อ: ถ้าเป็นแถวซ้ำของรายเดียวกัน → "รวมผู้ติดต่อ" (`MergeContactsAsync` `DocumentService.cs:14370` — มีตาข่ายเลขภาษีต่างกัน `:14383`) แล้วผูก · ถ้าคนละสาขาจริง → ยกเลิกแล้วออกใบให้ถูกสาขา
- เทียบด้วย `ContactId` เท่านั้น (ห้ามเทียบชื่อ/ fuzzy — F2 ข้อ 3) · หลังรวมผู้ติดต่อ เอกสารถูกย้าย `ContactId` แล้ว ⇒ ผ่านเอง
- ผู้จ่ายแทน (บุคคลที่สามโอนแทนลูกค้า) — ไม่เปลี่ยนผู้ติดต่อของใบเสร็จ (ใบรับออกให้ผู้ที่ชำระหนี้ของตน) · อยู่นอกขอบเขต v1 (258-1-4 ปิดข้ามผู้ติดต่อไว้แล้ว)

### 2f. สกุลเงิน
- เงินรอจัดสรร/จัดสรรภายหลัง = **บาทเท่านั้น** (258-1-13) · ข้อ 139 บังคับสกุลเดียวกัน ⇒ v1: ทั้งสองใบต้อง THB · ใบสกุลต่างประเทศ ⇒ ปฏิเสธพร้อมเหตุ (กำไร/ขาดทุน FX ของการย้ายยังไม่มีสูตร — ห้ามประทับอัตราเอง)

### 2g. คนละงวด / คนละรอบบัญชี / งวดปิด
- วันที่ JE ของการย้าย: งวดบัญชีของ**วันรับเงินเดิม**เปิดอยู่ ⇒ ลงวันที่นั้น (อายุลูกหนี้ย้อนหลังถูก) · ปิดแล้ว ⇒ **วันที่ทำรายการ** + หมายเหตุ (ลูกหนี้ ณ สิ้นงวดที่ปิดคงตามที่รายงาน — ไม่ restate) (266-1-7) ·
  ด่านงวดบัญชีตัวเดียวกับสมุดรายวัน (§6.0b X-9)
- ข้ามรอบบัญชีที่ปิดแล้ว (ปิดปี/ยอดยกมา) = วันที่ทำรายการเสมอ · ภาษี: งวด VAT ตาม §2a (ยื่นแล้ว = ปฏิเสธฝั่งถอย · งวดปัจจุบัน+ธงฝั่งรับ)
- เอกสารต่างรอบบัญชี (INV001 ปีนี้ · REC003 ปีก่อน) = เงินรับล่วงหน้าข้ามปี — ชั้นเงินทำได้ด้วยกฎข้างบน · แจ้งผู้ใช้ว่างบปีก่อนแสดงเป็นรายได้/ลูกหนี้ตามเดิม

### 2h. ใบร่าง · ยกเลิก · ปฏิเสธ
- INV001 ร่าง/รออนุมัติ = **ไม่มีลูกหนี้** ⇒ ผูกเงินไม่ได้ (258-1-18 เดิม: ไม่มี JE ตอนออกใบ = ปฏิเสธ) · ยกเว้น REC003 ร่าง (R0) ที่ตั้งต้นทางได้ (ผลเกิดตอนอนุมัติ REC003 ซึ่งตรวจ INV001 อีกครั้ง)
- ใบใดใบหนึ่ง `Voided/Rejected` / `IsDeleted` / ถูกแทน (`ReplacedByDocumentId`) ⇒ ปฏิเสธ
- ใบแจ้งหนี้ที่ถูกใบกำกับ supersede (TaxInvoice แปลงจาก Invoice) ⇒ เป้าหมายคือใบกำกับ (ใบที่ถือลูกหนี้จริง) — ตัวตัดสินต้องชี้ทาง

### 2i. e-Tax ส่งแล้ว
- REC003 (หรือใบแทน) ที่ถือ VAT และ e-Tax `Submitted/Accepted` หรือ e-Tax by Email ประทับเวลาแล้ว ⇒ ยกเลิกไม่ได้ ⇒ **ปฏิเสธการย้าย** (`RD-ETAX-RECEIPT-SENT` ชุดเดียวกับ `DecideAllocationReceiptsOnVoidAsync`) ·
  ใบเสร็จเปล่า (ไม่ถือ VAT) ไม่ได้ส่ง e-Tax Invoice แต่ถ้าส่งเป็น e-Receipt แล้ว = กติกาเดียวกัน
- INV001 ส่ง e-Tax แล้ว = ไม่กระทบ (กระดาษ INV001 ไม่เปลี่ยน · การรับเงินไม่ใช่เนื้อใบกำกับ) — ยกเว้นหัว "…/ใบเสร็จรับเงิน" ของใบกำกับที่ยกหัวไว้ (§2b) ⇒ ตัวตัดสินต้องห้ามผูกใบเสร็จแยกเข้าใบกำกับที่ `ServedAsReceipt=true` แล้ว (กระดาษสองใบอ้างว่าเป็นใบรับของเงินก้อนเดียว)

### 2j. ผลข้างเคียงนอกบัญชี
- **คู่ค้า A↔B** (`PartnerPaymentNotice` `CrossTenantWorkflow.cs:151` · `Document.PartnerSourceLinkId`): ฝั่ง B ถือใบแจ้งหนี้ซื้อที่ mirror INV002/INV001 + แจ้งชำระแล้ว ⇒ ย้ายเงินฝั่ง A ทำให้สถานะจ่ายของ B ผิด ⇒ v1 **ปฏิเสธ**เมื่อใบใดผูกคู่ค้าและมี notice/การชำระจากคู่ค้า (ทางไปต่อ: ให้ B ยกเลิกการแจ้ง/ประสานกัน) · รอบ 264 เป็นเจ้าของเส้นนี้
- **LINE/อีเมล/พอร์ทัลที่ส่งไปแล้ว**: REC003 ถูกส่งลูกค้าแล้ว ⇒ เมื่อยกเลิกและออกใบแทน ให้ส่งใบแทน + แจ้งยกเลิกใบเดิมผ่าน pipeline ส่งเดิม (ช่องทางตาม §2.12h ผู้ติดต่อเป็นเจ้าของปลายทาง) — **เลือกได้ในพรีวิว** ค่าตั้งต้น = ส่ง ·
  พอร์ทัลลูกค้าแสดงสถานะจาก `BalanceDue` สด ⇒ ตามเอง
- **ใบแจ้งยอด/อายุลูกหนี้**: อ่านสด (`CustomerCreditQuery` · aging) — INV001 หายจากค้าง · INV002 กลับมาค้าง ⇒ **พรีวิวต้องบอก** "INV002 จะกลับมาค้าง X บาท"
- **ทวงเงินอัตโนมัติ**: INV002 ที่กลับมาค้างอาจถูกทวงทันที (ตาราง §2.12g-0 · ระงับทวง 258-1-9/22) ⇒ พรีวิวเตือน + ตัวเลือก "เลื่อนการทวง INV002 N วัน" (ใช้ค่าตั้งเดิม ไม่สร้างกลไกใหม่) — ถ้าไม่มีกลไกเลื่อนต่อใบ = เตือนอย่างเดียว
- **รายการประจำ / งานหลังรับชำระ**: `PostPaymentAutomationRun` คีย์ด้วยการชำระ — การย้ายต้อง**ไม่**ยิงงานหลังรับชำระซ้ำ (ส่งใบเสร็จ/ขอบคุณ) ยกเว้นการส่งใบแทนที่ผู้ใช้ติ๊ก · `RecurringTransactionId` ของ INV001 ไม่เปลี่ยน
- **ใบสั่งขาย/ยอดวางบิล**: การผูกใบเสร็จไม่แตะ `SourceLineId` ⇒ ยอดที่วางบิลของ SO/QT ไม่เปลี่ยน (ถูก — นั่นคือการผูกใบแจ้งหนี้ ข้อ 139) · R5 ที่ตัดสต็อกแล้ว + INV001 ตัดสต็อก = สต็อกเบิ้ล → แก้ด้วยการยกเลิกใบซ้ำ (§2c) เท่านั้น

### 2k. Audit chain · ยกเลิกการผูก
- ทุกการผูก/ถอด เขียน `AddChainedAuditLog` (กฎ M) `RuleCode = DOC-RCPT-LINK` + `LegalReference` (`RD-86/4` · `RD-105` · `RD-78/1`) · before/after ของ `BalanceDue` ทั้งสองใบ + เลข JE + ใบแทน
- **ถอด (undo)** = ผ่านบริการเดียวกันเท่านั้น · กลับ JE ที่อ้าง `{เลข}/M{n}` · ปฏิเสธถ้ามีเหตุการณ์ที่พึ่งการผูกนี้ภายหลัง (INV001 มีการชำระ/ใบลดหนี้ใหม่ · ใบแทนถึงกรมสรรพากร · งวดภาษียื่นแล้ว) · ใบแทนที่ออกแล้วไม่ "คืนชีพ" REC003 (ใบที่ยกเลิกแล้วห้ามกลับมาใช้เลขเดิมเป็นใบรับ — ออกใบแทนอีกใบ) ⇒ undo ของ R3/R4 ที่ออกใบแทนแล้ว = **ไม่มี** (ทำการย้ายย้อนเป็นรายการใหม่แทน) (266-1-9)

### 2l. สิทธิ์ · API key · ชั้นความลับ
- ผูก = สิทธิ์**อนุมัติ**ชนิดของใบปลายทาง (แบบ `AllocateAsync` `CustomerCreditController.cs:114`) · ถ้าต้องออกใบแทน = + สร้าง+อนุมัติใบเสร็จ + **ยกเลิก**ใบเสร็จ (แบบ `reissue-settlement-paid`) · ถอด = สิทธิ์ยกเลิก (`:134`)
- SoD/วงเงินเซ็นหลายขั้น: ย้ายที่ออกใบแทน → `ApprovalControlPolicy.ForReissue` (ผู้ขอ ≠ ผู้ยืนยัน)
- API key/partner API: **ไม่เปิด**ใน v1 (เฉพาะผู้ใช้ในหน้าเว็บ) — ทางเข้าอัตโนมัติทั้งหมดคงปฏิเสธ (258-1-7)

### 4.6 สัญญากับรอบ 265 (ห้ามทำซ้ำ)
- 265 เป็นเจ้าของ: ตัวออกใบเสร็จ/ใบกำกับจากเงินเครดิต + ใบเสร็จรวม · 266 **อ่าน**เครื่องหมายที่ 265 ใช้บอกว่า "ใบนี้คือใบรับของการชำระ P (ไม่มีใบแจ้งหนี้)" — ถ้า 265 ใช้ `SettlementPaymentId` + `RelatedDocumentId=null` ให้ตกลงตามนั้น ห้ามเพิ่มช่องที่สอง

- การย้ายชิ้นของใบรวม = นอกขอบเขต 266 v1 จนกว่า 265 มีตัวออกใบรวมใหม่ที่ "แทน" ใบรวมเดิม
- ไฟล์ที่ 265 น่าจะแตะ (`DocumentService.CustomerCredit.cs` · `CustomerCreditService.*` · `customer-credits.html` · `CreateSettlementReceiptAsync`) — 266 แพ็ก A **ไม่แก้** ไฟล์เหล่านี้ (เรียกผ่าน interface เดิม) · แพ็ก B แตะได้หลัง 265 merge
