# รอบ 278 — ช่องลายเซ็น "ผู้เสนอราคา/ผู้จัดทำ" ↔ "ผู้มีอำนาจลงนาม" เป็นคนเดียวกัน

ที่มา: เจ้าของ (ภาพ QT-20261119-0001 ที่ระบบภายนอกสร้างผ่าน API) — ช่อง 1 "ผู้เสนอราคา" = "K.นัท" มีรูปลายเซ็น · ช่อง 2 "ผู้มีอำนาจลงนาม" =
"ณัฐพล ทรัพย์บวรโรจน์" ไม่มีลายเซ็น · ช่อง 3 ลูกค้าเซ็นออนไลน์ · "ช่อง 1 กับช่อง 2 เป็นคนเดียวกัน ... อันไหนมีลายเซ็นก็เอามาใส่ ชื่อไหนครบกว่าก็ใช้เป็นชื่อเดียวกัน"

## 1. วิเคราะห์ — ชื่อ/ลายเซ็นของแต่ละช่องมาจากไหน (ยืนยันกับโค้ด `PdfGenerationService.ResolveSignersAsync`)

| ทางเข้า | ช่อง 0 (ผู้จัดทำ/ผู้เสนอราคา/ผู้รับเงิน) | ช่อง 1 (ผู้มีอำนาจลงนาม — ใบอนุมัติแล้วเท่านั้น) |
| --- | --- | --- |
| สร้างด้วยมือ (เว็บ/มือถือ) | ผู้ใช้ CreatedBy (รูป+ชื่อจากโปรไฟล์) | ผู้อนุมัติใน `DocumentApprovals` → UpdatedBy → ผู้มีอำนาจลงนามที่บริษัทตั้ง (`UseCustomAuthorizedSignatory`) → ลายเซ็นเจ้าของเมื่อไม่มีชื่อเลย |
| **API key** `POST /api/companies/{id}/documents` (ภาพเจ้าของ) | `PreparerName` + `PreparerSignatureBase64` จาก payload ทับผู้ใช้ CreatedBy (= ผู้ออกคีย์) | ผู้ออกคีย์ (`ApiKeyMiddleware` NameIdentifier = `ApiKey.CreatedByUserId` ⇒ UpdatedBy) — **ไม่มีรูปในโปรไฟล์ ⇒ ช่องว่าง** |
| API v1 `DocumentsV1Controller` | CreatedBy = `api:v1` · ไม่รับผู้จัดทำ ⇒ ว่าง | ผู้อนุมัติ (ผู้ออกคีย์เมื่ออนุมัติผ่าน v1) |
| integration invoice/expense/PV | `PreparerName`/`PreparerSignatureBase64` (+ PV: `Payment.PayerSignature*`) | เหมือนด้วยมือ |
| LINE · OCR · convert · clone · recurring | ผู้กด/ผู้ตั้งรายการ (CreatedBy) · `PreparerName` ไม่สืบทอดลงใบลูก | เหมือนด้วยมือ |

**ทำไมทาง API ได้ชื่อเล่นกับไม่มีลายเซ็น:** ระบบต้นทางส่งชื่อเล่น "K.นัท" + รูปลายเซ็นมาใน payload (คนทำจริงไม่ใช่ผู้ใช้ NextAcc ในมุมของ payload) ·
ช่อง 1 คือผู้ออกคีย์ซึ่งเป็นคนเดียวกันแต่ไม่ได้อัปโหลดลายเซ็น · ระบบไม่มี**กุญแจ**ใดเชื่อม "ชื่อใน payload" กับ "ผู้ใช้" ⇒ ทำเป็นสองคน

### เลื่อน (ไม่ทำรอบนี้ + เหตุผล)
- **API v1 (`DocumentsV1Controller`) และ integration invoice/expense/PV ยังไม่รับ `preparerEmail`/`preparerUserId`** — ภาพเจ้าของมาจากเส้น API key ที่ endpoint เอกสารหลัก ·
  เส้นอื่นใช้กุญแจชื่อเล่นในโปรไฟล์ได้ทันที (ตัดสินตอนพิมพ์ ครอบทุกทางเข้า) · เพิ่มช่องใน payload เส้นอื่นเมื่อมีคู่ค้าต้องการ
- **ผู้มีอำนาจลงนามที่บริษัทตั้งเอง (`UseCustomAuthorizedSignatory`)** ไม่ใช่ผู้ใช้ ⇒ ไม่มีกุญแจ ⇒ ไม่รวม · ถ้าต้องการ ต้องเพิ่ม "ผูกกับผู้ใช้" ในหน้าตั้งค่า (เปลี่ยนความหมายค่าตั้ง — ต้องถามเจ้าของ)
- **fallback ฝั่ง client ใน documents.html** (`renderPdf` เมื่อ `generate-html` ล้ม) ยังใช้ลายเซ็นของผู้ดูคนปัจจุบัน — เป็นทางสำรองตอนเซิร์ฟเวอร์ล้มเท่านั้น ไม่แตะ

### ตรวจแล้วไม่ใช่บั๊ก
- "ทาง API ได้ชื่อเล่น" ไม่ใช่บั๊กของการเก็บ — ระบบต้นทางส่ง "K.นัท" มาเอง และ `PreparerName` ตั้งใจให้ priority เหนือ CreatedBy (กรณี TakeTime ผู้รับเงินเป็นพนักงานคนอื่นจริง) ⇒ ห้ามแก้ด้วยการทับชื่อจากผู้ออกคีย์โดยไม่มีกุญแจ

## 2b. ชุดแก้ฝ่ายค้าน (HIGH-1/2/3 + MED — ปลอมลายเซ็นได้) · คำตัดสิน 278-5…278-8 · commit SHA278B

| ข้อ | ปัญหาในรุ่นแรก (5304acd3) | แก้ |
| --- | --- | --- |
| HIGH-1 | รูปจาก payload ถูกคัดลอกเข้าช่องผู้มีอำนาจลงนาม ⇒ ใครถือ API key ก็ทำให้มี "ลายเซ็น" ใต้ชื่อกรรมการได้ · ผูก `preparerUserId` ของใครก็ได้ในบริษัท | ช่องผู้มีอำนาจลงนามรับเฉพาะรูปโปรไฟล์ของตัวเอง · ช่องผู้จัดทำรับรูปโปรไฟล์ของผู้ที่ผูกได้ (ทิศกลับ) · `preparerUserId`/`preparerEmail` ผูกได้เฉพาะผู้เรียกเอง (ผู้ออกคีย์) หรือผู้ที่เปิด "อนุญาตให้ระบบภายนอกระบุฉันเป็นผู้จัดทำ" · อื่น ๆ 400 · เทสต์ "กรรมการไม่มีรูป + payload มีรูป ⇒ ช่องกรรมการไม่มีรูป" |
| HIGH-2 | ชื่อเล่นระดับ User ตั้งเองมีผลทันที ข้ามบริษัท · ตั้งชื่อเป็นชื่อของคนอื่นได้ | ตาราง `SignerAliases` ต่อบริษัท · เจ้าของอนุมัติ (เจ้าของยื่นเอง = อนุมัติในตัว) · ห้ามคำกลาง · ห้ามซ้ำชื่อ/ชื่อเล่นของสมาชิกคนอื่นในทุกบริษัทที่ผู้ขอเป็นสมาชิก · ตรวจซ้ำตอนอนุมัติ · audit · `User.SignerAliases` ถูกถอด (ถ้า deploy รุ่นแรกไปแล้ว คอลัมน์ค้างในฐานแต่ไม่มีผู้อ่าน — ค่าที่ตั้งไว้ต้องยื่นใหม่ให้เจ้าของอนุมัติ) |
| HIGH-3 | กติกาใหม่เปลี่ยนเอกสารที่ออกแล้วย้อนหลัง | แช่แข็งตอนออกเอกสาร (`StampSignerFreeze` ใน SaveChanges — ทุกทางเข้า) · ใบที่ออกก่อนรอบนี้ = snapshot ว่าง (`Round278Migration`) · เปลี่ยนการผูกบนใบที่ออกแล้ว = 400 · ปุ่ม "ปรับผู้ลงนาม" (เจ้าของ · เหตุผล · audit · ไม่ใช่หลักฐานภาษี/เงิน · ลูกค้ายังไม่เซ็น) |
| MED | redact ชื่อเล่น · ไม่มี audit | ถอดจาก redact · audit แถว `SignerAlias` (เพิ่ม/อนุมัติ/ยกเลิก) + สิทธิ์ผูก (`CompanyUser`) · snapshot อยู่ใน audit ของเอกสารพร้อม RuleCode |

**ทำไม QT-20261119-0001 ของเจ้าของคงตามเดิม:** ลูกค้าเซ็นยอมรับใบนี้ออนไลน์แล้ว — ลูกค้าเห็นและยอมรับกระดาษที่ช่องผู้มีอำนาจลงนามว่าง · ถ้าระบบเติมชื่อ/ลายเซ็นหลังลูกค้าเซ็น
เอกสารที่ลูกค้าถือกับที่ระบบพิมพ์จะไม่ตรงกัน (หลักฐานการยอมรับเสียความน่าเชื่อถือ) · ใบนี้ออกก่อนรอบนี้ ⇒ snapshot ว่าง · ปุ่มปรับก็ปฏิเสธเพราะลูกค้าเซ็นแล้ว ·
ใบเสนอราคาถัดไปที่ระบบภายนอกส่ง "K.นัท" มา จะได้ชื่อเต็มทั้งสองช่องเมื่อชื่อเล่นได้รับอนุมัติก่อนออกใบ · ช่องผู้มีอำนาจลงนามจะมีรูปเมื่อคุณณัฐพลอัปโหลดลายเซ็นในโปรไฟล์

### ตรวจเพิ่มหลังชุดแก้
- เส้นที่เปลี่ยนสถานะด้วย SQL ตรง (`ExecuteUpdate`) ไม่ผ่าน SaveChanges ⇒ ไม่ได้แช่แข็ง ⇒ null = ไม่รวม (ทิศปลอดภัย) และได้ snapshot ว่างที่การบูตถัดไป
- ผู้จ่ายเงิน PV (`Payment.PayerSignatureName`) ไม่ใช่กุญแจชื่อเล่น (snapshot ดูเฉพาะ `PreparerName`) — ไม่รวม

## 3. สิ่งที่เจ้าของต้องทำหลัง deploy
1. คุณณัฐพลเปิด **ลายเซ็นของฉัน** (เลือกบริษัทนี้) → "ชื่อเล่นที่ระบบภายนอกใช้เรียกฉัน" ใส่ `K.นัท` → บันทึก (ถ้าคุณณัฐพลเป็นเจ้าของบริษัท ⇒ อนุมัติในตัว · ถ้าไม่ใช่ เจ้าของกดอนุมัติในหน้าลายเซ็นของฉันของตัวเอง)
   ⇒ ใบที่ออก**หลังจากนั้น**ที่ส่ง "K.นัท" มาจะพิมพ์ชื่อเต็มทั้งสองช่อง · อัปโหลดลายเซ็นในโปรไฟล์ถ้าต้องการรูปในช่องผู้มีอำนาจลงนาม
2. QT-20261119-0001 คงตามเดิม (ลูกค้าเซ็นยอมรับแล้ว — §2b) · ใบเสนอราคาอื่นที่ออกไปแล้วและลูกค้ายังไม่ยอมรับ ใช้ปุ่ม "ปรับผู้ลงนาม" ในหน้าพิมพ์ได้ (ต้องระบุเหตุผล)
3. (ทางเลือก) ให้ระบบภายนอกส่ง `preparerEmail` ของ**ผู้ออกคีย์เอง** — หรือของผู้ใช้อื่นที่เปิด "อนุญาตให้ระบบภายนอกระบุฉันเป็นผู้จัดทำ" แล้ว
4. ตรวจในเครื่องนี้: build + เทสต์ที่เกี่ยวข้องผ่าน (ไม่ได้รอ CI ตามคำสั่ง) — ดูผลชุดเต็มที่ CI ของ branch
