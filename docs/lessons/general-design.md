- **แยกของออกเป็นหลายชิ้น = ต้องถามทุกฟิลด์ว่า "เป็นเปอร์เซ็นต์ หรือจำนวนเงิน"**
  แยกบิล POS สร้างใบลูกโดยไม่สืบทอด `DiscountPercent`/`ServiceChargePercent`
  แล้วคิดยอดใหม่จาก 0 ⇒ ร้านที่คิดค่าบริการ 10% **เสียรายได้ส่วนนั้นทุกครั้งที่
  แยกบิล** (งานประจำวันของร้านอาหาร ไม่ใช่ edge case) และบิลที่ให้ส่วนลดท้ายบิล
  **เก็บลูกค้าเกิน**. ทั้งสองเงียบสนิทเพราะยอดของแต่ละใบ "ดูสมเหตุสมผล" — ไม่มี
  ใครเอาผลรวมของใบลูกไปเทียบกับใบแม่
  → กติกา: ค่า **เปอร์เซ็นต์** สืบทอดตรง ๆ ได้ (เชิงเส้น ⇒ ผลรวมเท่าเดิมพอดี) ·
  ค่าที่เป็น **จำนวนเงินก้อน** (คูปอง/ทิป) แบ่งไม่ได้โดยไม่เดา → **บล็อกพร้อมบอก
  ทางแก้** ดีกว่าเฉลี่ยเอาเองหรือทิ้งไว้ที่ใบแม่เงียบ ๆ · และเขียนเทสต์ที่ยืนยัน
  **invariant ผลรวมของชิ้นย่อย = ของเดิม** เพราะนั่นคือสิ่งเดียวที่จับบั๊กคลาสนี้ได้

- **ลืม `AwayFromZero` ≠ ยอดผิด — แต่ "ตกจุดกึ่งกลางได้" ก็ไม่ใช่ทุกสูตร**
  (ต่อจากบทเรียน `VatRoundingMode`) รอบนี้ไล่ค่าจริงก่อนแก้: `x / 2` ตกจุด
  กึ่งกลาง **ทุกครั้งที่สตางค์เป็นเลขคี่** · `x × 0.15` ตกที่สตางค์ ≡ 10 (mod 20)
  · **`x × 0.20` ไม่เคยตกเลย** (ไล่ 2 ล้านค่า) → สองตัวแรกเป็นบั๊กจริง ตัวที่สาม
  ใส่ให้เหมือนกันทั้งเมธอดในฐานะ **การป้องกัน** และ**จดไว้ว่าตัวไหนเป็นตัวไหน**
  ไม่งั้นรอบหน้าจะมีคนอ่าน commit แล้วเข้าใจว่าทั้งสามเคยผิด

- **`Debug.WriteLine` ไม่ใช่การ "ดัง" — มันถูกคอมไพล์ทิ้งใน Release**
  `SequenceNumber.NextAsync` เตือนว่า "ออกเลขนอก transaction ⇒ advisory lock ถูก
  ปล่อยก่อน insert" ด้วย `Debug.WriteLine` **พร้อมคอมเมนต์ที่เขียนเองว่า "ต้องดัง
  พอให้เห็นตอนตรวจ log (กติกาห้ามเงียบ)"** — บนเครื่องจริงบรรทัดนั้นไม่มีอยู่เลย
  ⇒ คำเตือนที่ตั้งใจให้ดัง เงียบสนิทในที่เดียวที่มันสำคัญ (ญาติของบทเรียน
  "`LogWarning` แล้วเดินต่อ = ดังในที่ที่ไม่มีคนดู") → ยิงผ่าน `ILogger` จริง
  (static property ตั้งครั้งเดียวตอน boot) และ fallback `Console.Error` เมื่อยัง
  ไม่มีใครตั้ง — **ห้ามมีทางที่คำเตือนหายไปทั้งหมด**

- **unique index ที่ไม่กรอง `IsDeleted` ⇒ soft-delete แล้วสร้างชื่อเดิมใหม่จะชน** `IX_SitePages_SiteId_Slug`
  ไม่กรองแถวที่ลบแล้ว ⇒ ลบหน้า `booking` แล้วสร้างใหม่ slug เดิม = 500 แบบสุ่มที่ผู้ใช้อ่านไม่ออก
  → ย้าย slug ของแถวที่ปลดออกไปให้พ้นทางด้วย helper ตัวเดียว (`Helpers/CmsRetiredSlug`) ที่ทั้งเส้นลบและ
  เส้นเติมเทมเพลตเรียก — ห้ามเขียน format string สองที่ (กติกาเดียวกับ hash/signature)

- **แก้ให้ "ลูก" แต่ลืม "แม่" — index รูปแบบเดียวกันคนละตาราง (รอบ 171, ผู้ใช้เจอเอง REF:F37BE341)**
  บทเรียนข้อบนแก้ `IX_SitePages_SiteId_Slug` ไปตั้งแต่รอบ 158 **แต่ตาราง `Sites` เองมีรูปแบบเดียวกัน
  เป๊ะและไม่ถูกแตะ** ⇒ ผู้ใช้ลบเว็บชื่อ `b1` แล้วสร้างใหม่ชื่อเดิม ได้ 500 ที่อ่านไม่ออก
  (`23505 IX_Sites_CompanyId_Slug`). ซ้ำร้าย `CreateSiteAsync` ตรวจซ้ำ **เฉพาะ Subdomain
  ไม่เคยตรวจ Slug เลย** ⇒ แม้ไม่เคยลบอะไร ถ้าตั้งชื่อเว็บซ้ำกับเว็บที่ยังใช้งานอยู่ก็ 500 เหมือนกัน
  — สองบั๊กคนละสาเหตุแต่โผล่ที่หน้าจอเดียวกัน
  → กติกา: บทเรียนที่ขึ้นต้นว่า "index ตัว X ไม่กรอง `IsDeleted`" **ต้องปิดท้ายด้วยการกวาด
  `HasIndex(...).IsUnique()` ทั้ง DbContext ในวันเดียวกัน** ไม่ใช่แก้เฉพาะตารางที่ผู้ใช้เจอ —
  รอบนี้กวาดแล้วพบ **62 entity ที่มีทั้ง unique index และ query filter `!IsDeleted`** และในนั้น
  **9 ตัวคีย์เป็น "รหัสที่ผู้ใช้พิมพ์เอง"** จึงมีอาการเดียวกันรออยู่ (`Product.Code` ·
  `ProductCategory.Code` · `Warehouse.Code` · `Branch.Code` · `Department.Code` · `Position.Code` ·
  `Project.Code` · `ChartOfAccount.AccountCode` · `SiteCustomer.Email`) — ยังไม่แก้ในคอมมิตเดียวกัน
  เพราะการปลดรหัสตอนลบเปลี่ยนสิ่งที่รายงานย้อนหลังแสดง (ERP core) ต้องให้เจ้าของตัดสิน
  จดไว้ใน `CHANGELOG.md` รอบ 171 · ระหว่างนี้ทั้ง 9 ตัวได้ข้อความ 409 ที่อ่านออกจาก
  `ExceptionMiddleware` ซึ่งแปลง Postgres 23505 แล้ว (ครอบทุกตาราง ไม่ใช่แค่ CMS)
  _(สองบทเรียนซ้อน — (1) **ค่าที่ผู้ใช้พิมพ์เอง กับค่าที่ระบบสร้างให้ ต้องปฏิเสธคนละแบบ**:_
  _Subdomain ผู้ใช้พิมพ์ → บอกให้เปลี่ยน · Slug ระบบสร้างจากชื่อเว็บและ **ไม่มีช่องให้แก้ในฟอร์ม**_
  _→ ต้องเติมเลขต่อท้ายให้เอง การโยน error ว่า "slug ซ้ำ" คือทางตัน ผู้ใช้ไม่เคยเห็นคำนี้มาก่อน_
  _(2) **ตัวตัดข้อความที่ถือความยาวของตัวเองจะเพี้ยนเมื่อเอาไปใช้กับคอลัมน์อื่น**:_
  _`CmsRetiredSlug.MaxLength` เดิม hardcode 256 ตาม `SitePage.Slug` — เอาไปใช้กับ `Site.Subdomain`_
  _(63) จะได้สตริงยาวเกินแล้ว insert ล้มโดยคอมไพเลอร์ไม่จับ ⇒ ย้ายความยาวทุกคอลัมน์ไปไว้ที่_
  _`Helpers/CmsFieldLengths` แล้วให้ `AccountingDbContext` อ่านตัวเดียวกัน)_

- **เก็บ + echo ครบ ≠ มีผล — ค่าตั้งที่ไม่มีผู้อ่าน** (รอบ 193 · `erp-review/2026-09-24/audit-settings.md` S-06 · ทีม W) — กฎ #4 A
  "เก็บแล้วต้อง echo กลับ" ผ่านครบ (ฟอร์ม → DTO → entity → migration → response → hydrate) แต่**ไม่มีโค้ดสักบรรทัดที่อ่านค่าไปตัดสินอะไร**
  ⇒ ผู้ใช้ตั้ง `AutoCloseMonthEnd` แล้วเชื่อว่ามีการควบคุมภายใน · ตั้งหมายเหตุท้ายใบกำกับในหน้าตั้งค่าแล้วไม่ขึ้นบนกระดาษ (PDF อ่าน
  `DocumentTemplate.FooterNotes`) · ปิดสวิตช์ API Access แล้วคีย์ที่ออกไปยังใช้ได้ · ติ๊ก "ผู้ประกอบการขาย/ซ่อมรถ" แล้ว OCR ยังปิดเคลม
  (ผู้อ่านมี แต่ไม่ถึงทุกทางเข้า) — 18 ช่องบนหน้าจอ + ~80 ฟิลด์ใน entity. "มีช่อง" ทำให้ผู้ใช้เชื่อว่ามีผล ซึ่งแย่กว่าไม่มีช่อง
  → กลไก: `tools/settings_reader_check.py` (ratchet · นับผู้อ่านจริง ไม่นับ echo/คำขอ/คัดลอก/หน้าแก้ค่าเอง · `--self-test` ถอดผู้อ่านจริงแล้วต้องฟ้อง) ·
  ช่องที่ยังไม่มีผล = **ล็อก + ป้าย "ยังไม่รองรับ — ค่านี้ยังไม่มีผลกับระบบ" + ไม่ส่งตอนบันทึก** (ไม่ลบคอลัมน์ — "ต่อสาย หรือ ลบ" เป็นคำตัดสินเจ้าของ) ·
  ข้อจำกัดที่ต้องรู้: checker ตอบได้แค่ "มีผู้อ่านไหม" ไม่ตอบ "อ่านครบทุกทางเข้าไหม" (S-01/S-02/S-05 ต้องพึ่ง resolver ตัวเดียว + เทสต์)

- **จับคู่แบบ fuzzy แล้ว "เขียนกุญแจถาวร" = เปลี่ยนความผิดพลาดรายใบเป็นความผิดพลาดถาวร** (รอบ 193 · ฝ่ายค้านรอบสาม R3-2 · ทีม C3) —
  การเติมเลขภาษีให้แถวผู้ติดต่อที่ "จับได้แล้วแต่ยังไม่มีเลข" (`AdoptTaxId`) ถูกเรียกหลัง `CounterpartyNameMatcher` (ชื่อคล้ายข้ามภาษา) และ
  `Name.Contains(...)` ที่ไม่มี OrderBy ⇒ ก่อนหน้านั้นการจับผิดตัวผิดแค่ "เอกสารใบนั้น" (แก้รายใบได้) · หลังจากนั้นเลขภาษีของผู้ซื้อ A ถูกเขียนลงแถว B
  **ถาวร** ⇒ `FindAsync(เลข A)` ได้แถว B ทุกครั้ง ⇒ ใบกำกับของ A พิมพ์ชื่อ/ที่อยู่ B (§86/4 ผู้ซื้อผิดตัว) และไม่มีร่องรอยให้แยกกลับ
  → กติกา: **การเขียนกุญแจ (เลขภาษี · ExternalId · สาขา) ต้องอาศัยหลักฐานระดับกุญแจ** — ชื่อเท่ากันหลัง normalize / อีเมล / รหัสภายนอก
  เท่านั้น (superstring ไม่ใช่ fuzzy — กฎ #4 H) · fuzzy ยังใช้ "ผูกเอกสาร" ได้ แต่ถ้า payload มีเลขจริงให้สร้างแถวใหม่ ·
  กลไก: `AdoptTaxId(row, taxId, branch, ContactMatchKind)` → `ContactAdoptOutcome.Reject` เป็น**พารามิเตอร์บังคับ** (ผู้เรียกลืมไม่ได้) +
  `NameMatchKind` ตัวเดียว + `required_call_site_check` บังคับให้ทุกผู้เรียกจัดการ `Reject`

- **ตัวอ่าน "ค่าแรกที่ไม่ว่างทีละช่อง" บนคำตอบหลายแถว = ประกอบระเบียนข้ามแถว** (รอบ 193 · ทีม O2 · คำตัดสิน #18) — ทะเบียน VAT ของกรมสรรพากร
  ตอบหลายแถว (สนญ. + สาขา) ในลิสต์คู่ขนาน · ตัวอ่านเดิมหยิบ "ค่าแรกที่ไม่ว่าง" ทีละช่อง ⇒ ได้เลขบ้านของสาขา + ตำบลของ สนญ. เป็นที่อยู่เดียว
  (ไม่มีแถวไหนในทะเบียนเป็นแบบนั้น) — และมี**สองสำเนา** (`DbdLookupService` · `ThaiGovIntegrationService`)
  → กติกา: เลือก**แถว**ก่อนแล้วอ่านทั้งแถว (`RdVatBranchRecords.PickForBranch`) · ระบุแถวไม่ได้ = "ชื่ออย่างเดียว ที่อยู่ว่าง" (ไม่รู้ ≠ แต่ง)

- **จับด้วยกุญแจครึ่งเดียว แล้วเขียนอีกครึ่งทับ** (รอบ 193 · ทีม O2 → C3 · คำตัดสิน #20) — `IntegrationService.ProcessCustomerAsync` หาผู้ติดต่อด้วย
  เลขภาษีอย่างเดียว (ได้แถว สนญ.) แล้วบล็อก update เขียน `BranchCode = 00008` + ที่อยู่สาขาทับ ⇒ แถว สนญ. หายโดยไม่มีอะไรฟ้อง ·
  ทางเข้าอื่นอีก 19 จุด/13 ไฟล์จับด้วยเลขอย่างเดียว (2 จุด `ToDictionary(c => c.TaxId)` **โยนทั้งไฟล์**เมื่อเลขเดียวมีสองสาขา) ·
  รหัสสาขาผิดรูป "8A" ถูกตัวจับคู่ตีว่า "ไม่รู้" (ได้แถว สนญ.) แต่ตัวเขียนดึงเลขออกเป็น 00008 = ช่องเดิมผ่านอีกประตู
  → กติกา: ตัวจับคู่ต้องตอบด้วยว่า "**เขียนครึ่งที่เหลือได้ไหม**" (`ContactKeyMatch.MayOverwriteBranch`) ไม่ใช่แค่ "เจอแถวไหน" ·
  กลไก: `tools/contact_taxid_only_match_check.py` (กติกา 1 เลขอย่างเดียว · กติกา 2 จับชื่อ/อีเมลนอก `SoftScope`)
