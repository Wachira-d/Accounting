- **ลิงก์ไปหน้าที่ไม่มีอยู่จริง — ไม่มี compiler ตัวไหนจับให้** ปุ่ม "เปิด →"
  ในหน้าสำนักงานบัญชีพาไป `/pages/dashboard.html` ซึ่ง **ไม่เคยมีไฟล์นั้นอยู่
  จริงเลยสักวันเดียว** (แดชบอร์ดจริงคือ `/simple.html` หรือ `/app.html` ตาม
  `uiMode`) — ผู้ใช้เจอ ERR_INVALID_RESPONSE. พาธเดียวกันมีอีก 3 จุด (ตอบรับ
  คำเชิญ · ปุ่ม "กลับระบบหลัก" ใน Connect portal · ออกจาก POS) และเจอ
  `/pages/document-template.html` (เอกพจน์ ไฟล์จริงพหูพจน์) ในเช็กลิสต์เริ่มต้น
  ใช้งานอีก 1 จุด. เคยแก้ไปแล้ว **1 จุด** (pos.html) แต่ที่เหลือถูกทิ้งไว้ —
  defect class "แก้ตัวเดียว เหลือที่เหลือ"
  _(ลิงก์ที่ชี้ผิดเป็น string ที่ถูกต้องทางไวยากรณ์ทุกประการ ⇒ `node --check`
  และ checker ฝั่ง C# ทั้งหมดมองไม่เห็น ต้องเช็คกับระบบไฟล์เท่านั้น → เพิ่ม
  `tools/dead_link_check.py`. ปลายทางที่มีหลายหน้าให้ผ่าน resolver กลาง
  `Layout.dashboardUrl()` และ **ต้องทิ้งหน้า redirect ไว้ที่ URL เดิม** เพราะ
  ลิงก์ในอีเมลคำเชิญที่ส่งออกไปแล้ว/บุ๊กมาร์กของผู้ใช้ แก้ย้อนหลังไม่ได้)_

- **`.modal-footer` ไม่มี `flex-wrap` บนเดสก์ท็อป** (มีเฉพาะใน `@media` มือถือ)
  + `justify-content:flex-end` ⇒ modal ที่มีปุ่มเยอะ (หน้ารายละเอียดเอกสารมีได้ถึง
  10 ปุ่ม) ล้นออกนอกกรอบ และส่วนที่ล้นหลุดออกทาง**ซ้าย** = ปุ่มแรก ๆ ถูกตัดหาย
  กดไม่ได้เลย. แก้ที่ `.modal-footer` จุดเดียว = ทุก modal ทั้งระบบปลอดภัยพร้อมกัน
  · แถบปุ่มที่ยาวจริงให้จัดกลุ่มด้วย `data-g="primary|more|danger"` + เมนู
  "⋯ เพิ่มเติม" (`_layoutDetailActions`) — **ปุ่มที่ลืมติดป้ายต้องถือเป็น primary**
  (ปุ่มใหม่ต้อง "เห็น" ไม่ใช่ "หาย") และคำสั่งอันตรายอยู่ท้ายเมนูหลังเส้นคั่น

- **slug พิเศษของ storefront ห้ามแย่งหน้า CMS ที่ seed ไว้โดยไม่ probe ก่อน** — `/booking` และ `/rooms`
  เป็นหน้า `SitePage` ที่ `CmsSiteTemplateSeeder.HotelPlan` สร้างให้ทุกเว็บโรงแรม; โมดูลที่พักอยาก
  ยึด slug เดียวกัน (ให้ปุ่ม "จองห้องพัก" ที่ seed ไว้พาไประบบจองจริงโดยไม่ต้องแก้เทมเพลต) ⇒
  `tryRouteSpecialSlug` ต้อง `fetch /lodging/info` **ก่อน** แล้วยึดเฉพาะเมื่อมีที่พักผูกจริง —
  เว็บสปา/คลินิกที่ใช้บล็อก BookingCalendar แบบ slot ต้องไม่ถูกกระทบ (ทดสอบ LDG-S-02)

- **ค่าที่ "รับมาใช้ครั้งเดียวแล้วทิ้ง" = ระบบลืมทันที และประตูปิดตาย** `CreateSiteRequest.IndustryType`
  ถูกใช้เลือกเทมเพลตตอนสร้างเว็บ แล้ว**ไม่เคยเก็บลง `Site`** ⇒ (ก) ไม่มีใครรู้ว่าเว็บไหนเป็นที่พัก — แถบเมนู ·
  แท็บใน cms-edit · การ์ดในหน้ารายการ ต้องเดาจาก**ผลข้างเคียง** (มี `LodgingProperty` ไหม · `SiteType` อะไร)
  ซึ่งเดาผิดได้ทั้งคู่ (ที่พักก็เป็น `SiteType.Booking` เหมือนสปา) (ข) **เว็บที่สร้างผิดประเภทซ่อมไม่ได้เลย**
  ทางเดียวคือลบทิ้งแล้วสร้างใหม่ = เสีย subdomain/โดเมน/ออเดอร์/ลูกค้าที่ผูกอยู่
  → กติกา: ค่าที่ **ตัดสินหน้าตา/ฟีเจอร์ของสิ่งที่สร้าง** ต้องถูกเก็บไว้กับสิ่งนั้นเสมอ ไม่ใช่ใช้แล้วทิ้ง ·
  และทุก "ตัวเลือกตอนสร้าง" ต้องมีคู่แฝดเป็น "ตัวแก้ทีหลัง" (ที่นี่ `POST …/apply-template`) —
  ญาติของบทเรียน "สถานะปลายทางที่ผู้ใช้ไปต่อไม่ได้ = ฟีเจอร์ที่ยังไม่จบ"
  _(อาการที่ผู้ใช้เห็น: เลือกการ์ด "โรงแรม/ที่พัก" แล้วได้เว็บบริการทั่วไป ไม่มีหน้าจอง — เพราะ dropdown_
  _"ประเภทธุรกิจ" ค้างที่ค่าแรกแล้ว payload อ่าน dropdown เป็นตัวตัดสิน ⇒ **เทมเพลตแพ้ทุกครั้ง**._
  _ตัวเติมฟอร์มที่มีหลายเจ้าต้องใช้ `autoSrc`/`userTouched` แบบเดียวกับ `Layout.setLineVat` — ไม่ใช่ปล่อยให้_
  _"ค่า default ที่ไม่มีใครแตะ" ชนะสิ่งที่ผู้ใช้เพิ่งกดเลือก)_

- **หน้าที่ถูก "ยึด slug" โดยโมดูลอื่น = แก้แล้วไม่มีผล (silent no-op ที่ไม่มี error ให้ debug)**
  storefront ยึด `/booking` `/rooms` ให้ระบบจองห้องเมื่อเว็บมีที่พัก ⇒ หน้า CMS ที่ seed ไว้ slug เดียวกัน
  **แก้จาก cms-edit แล้วไม่มีอะไรเปลี่ยน** (แต่ยังอยู่ในเมนูเว็บ ผู้ใช้จึงคิดว่ามันคือหน้านั้น)
  → เมื่อยึด slug ให้เก็บส่วนที่เจ้าของแก้ได้ไว้อย่างน้อยหนึ่งอย่าง (ที่นี่: วาด Hero ของหน้า CMS เหนือระบบจอง)
  หรือไม่ก็อย่า seed หน้าที่จะถูกยึดเลย — การปล่อยให้มีหน้าที่แก้แล้วไม่มีผลคือทางที่แย่ที่สุด

- **ปุ่ม/ฟอร์มที่ตอบ "สำเร็จ" โดยไม่ส่งอะไรเลย คือการโกหกผู้ใช้ปลายทาง** บล็อก Newsletter บนเว็บลูกค้า
  เขียน `onsubmit="alert('สมัครเรียบร้อย!');return false"` — อีเมลที่ผู้เยี่ยมชมกรอกหายไปเฉย ๆ ทุกใบ
  (ญาติของ "โหมดออฟไลน์ที่ประทับสถานะปลายทางให้เอง") → ต่อเข้าเส้น lead ที่มีอยู่แล้ว ไม่ใช่เขียนเส้นใหม่

- **ค่าตั้งต้นของ "ระบบจริง" กับ "ข้อความโฆษณาบนหน้าเว็บ" ต้องมาจากตารางเดียว** หน้าเว็บที่ระบบ seed ให้
  เว็บโรงแรมพิมพ์ "Junior Suite ฿3,800 · 4 ประเภท · เช็คอิน 15:00 · ยกเลิกฟรีก่อน 3 วัน · ราคารวมอาหารเช้า"
  ขณะที่ที่พักที่ seed ให้จองจริงมี **3 ประเภท · 14:00 · 7 วัน · อาหารเช้าเป็นแผนราคาแยก** — สอง seeder
  เขียนตัวเลขเองคนละชุดตั้งแต่วันแรก (doc-comment ของตัวหนึ่งยังเขียนว่า "ตัวเลขตรงกับหน้าเว็บ" อยู่เลย)
  ⇒ แขกอ่านราคา/กติกาบนหน้าแรกแล้วไปเจออีกอย่างตอนจอง → ยุบเป็น `Helpers/LodgingSeedDefaults` +
  **เทสต์ที่ล็อกสองทิศ** (ต้องมีทุกค่าจากตาราง · ต้อง**ไม่มี**ค่าที่เลิกใช้แล้ว) ไม่ใช่ล็อกแค่ทิศเดียว

- **ป้ายที่ "ยืนยันข้อเท็จจริง" ติดได้เฉพาะตอนที่เรามีข้อเท็จจริงนั้นจริง**
  `Layout.setTitleSelectValue` ติดป้าย `⚠️ ไม่อยู่ในตารางของกรมสรรพากร` ให้ค่าที่ไม่
  อยู่ใน options — แต่เมื่อ `fetch /api/reference/titles` ล้ม options ว่างทั้งชุด ⇒
  **ทุกค่ารวมทั้ง "นาย" ติดป้ายว่าผิด** ทั้งที่เราแค่โหลดตารางไม่ได้ (เรา*ไม่รู้*
  ไม่ใช่*รู้ว่าผิด*) ⇒ สอนผู้ใช้ให้เมินคำเตือนทั้งกล่อง = ปิดด่านโดยไม่ได้ตั้งใจ ·
  และ `catch → console.warn` ทำให้ช่องที่บังคับกรอกเหลือตัวเลือกเดียวโดยไม่มีอะไรบอก
  → ติดป้ายเฉพาะเมื่อ `_titlesCache` โหลดมาได้จริง + toast บอกเหตุและทางไปต่อ

- **`innerHTML +=` บน container ที่ลูกผูก listener แบบ async = ปุ่ม/ช่องลากไฟล์ตายเงียบ** (รอบ 190 ทีม U) — `+=` แปลง DOM ทั้งก้อนเป็น
  ข้อความแล้วสร้างใหม่ ⇒ listener ที่ผูกไว้กับลูกเดิมหายหมด (ไม่มี error) ⇒ "คลิกหรือลากไฟล์เพื่ออัปโหลดไม่ได้" บนหน้ารายละเอียดเอกสาร ·
  ใช้ `insertAdjacentHTML`/`appendChild` · ไม่ทำ checker เพราะ 23 จาก 24 จุดในเรพปลอดภัย (เติม `<option>`/ข้อความ) และการแยกต้องรู้ว่า
  container มีลูกที่ผูก listener ไหม = ฟ้องผิดแน่ (F2 ข้อ 6)
